## 1. 系统概览

### 1.1 它解决什么问题

在一台服务器上以**可控的资源开销**完成（实际占用以部署环境实测为准；默认 core 规则档、
日志采集模式下，检测环节通常只占单核个位数百分比）：

1. **实时看清流量**：带宽利用率、包速率、并发连接、TOP 会话、端口流量分布（模块 3.1）；
2. **自动发现异常**：非标准端口高频访问、端口扫描、暴力破解、突发流量峰值（模块 3.2）；
3. **自动处置与通知**：命中高危策略即联动 iptables/nftables/firewalld 封禁，并推送到钉钉/企微/邮件/Syslog（模块 3.3）；
4. **提醒风险并给修复建议**：扫描资产指纹 → 匹配 CVE 知识库 → 输出修复版本与可执行建议（模块 3.4）；
5. **维护资产台账**：被动学习内网主机与开放端口，主动指纹识别，关联历史告警与漏洞（模块 3.5）。

### 1.2 页面地图（共 9 个页面 + 兼容跳转）

### 1.3 角色视角

| 角色 | 常用页面 | 主要动作 |
| --- | --- | --- |
| viewer（只读） | 监控大屏、威胁告警、封禁管理 | 查看态势与证据；不能封禁/改规则/导出报告 |
| analyst（分析） | 威胁告警、封禁管理、异常端口 | 研判证据、确认告警、封禁/解封、生成报告、导出 |
| admin（管理） | 规则管理、所有页面 | 规则档位/后端切换、重载、用户与审计、全部处置 |

### 1.4 权限与鉴权

* 默认 `AUTH_ENABLED=true`：所有页面与 API 都要求登录；未登录页面跳 `login.html`，API 返回 401；
* 浏览器使用 **服务端会话 Cookie**（HttpOnly）＋ 写请求 `X-CSRF-Token`；角色分 `admin/analyst/viewer`；
* 机器调用（代理/WAF/脚本）使用 `X-API-Token`（需在 `.env` 配置非空 `API_TOKEN`），不受 CSRF 限制；
* 登录失败限流、连续失败锁定、登录/登出/封禁/规则/报告/导出全部写审计；
* 用户管理在「规则管理 → 用户与审计」（admin 可见）：新建、改角色、停用/重新启用、重置密码；用户名 2–64 位（中文/字母/数字/`_.@-`）；停用/改角色会踢出该用户所有会话；系统始终保留至少一个启用中的 admin，不能把最后一个 admin 降级或停用；
* 应急降级：`AUTH_ENABLED=false` 会退回“仅 Token”的旧行为，**仅限内网且需审批**。

### 1.5 详情浮窗的统一交互

各页面的「详情 / 建议」按钮打开的是同一套**右侧详情浮窗**（抽屉），行为统一为：

* **默认不显示**：页面加载、定时刷新、SSE 推送都不会弹出浮窗；只有主动点击列表里的「详情」
  （漏洞页为「建议」）才会从右侧滑入，不会遮挡常态看板；
* 打开时背景变暗并屏蔽点击，避免误触列表里的其它按钮；
* 浮窗内容与点击的那一行一一对应（标题带告警编号 / 资产 IP / CVE 编号），并可在浮窗内直接处置
  （确认封禁、确认关闭、推进漏洞状态、重新扫描该资产）；
* **三种关闭方式**：右上角 `×`、点击浮窗外的遮罩区域、按 `Esc`；
* 浮窗内的处置动作成功后会自动关闭并刷新列表，保证看到的是最新状态。

## 2. 快速启动（三种方式）

### 2.1 看演示（30 秒，无需后端）

直接双击打开 `dashboard/index.html`。探测不到后端时会自动进入**演示数据模式**：

* 右上角显示「演示数据」徽标；
* 每 25~40 秒自动上演一次攻击剧本（端口扫描 / 暴破 / 非标准端口 / 突发峰值）；
* 所有模块页面同样可用，且封禁、解封、扫描、状态流转等**处置动作可点击生效**（作用于浏览器内存）。

> 演示模式适合评审、培训与前端联调，不要用于真实判断网络状况。

### 2.2 本地/服务器直跑（推荐用于生产）

```bash
# 1) 安装依赖
python -m venv .venv
.venv/Scripts/python -m pip install -r backend/requirements.txt      # Windows
# source .venv/bin/activate && pip install -r backend/requirements.txt  # Linux/macOS

# 2) 启动服务（Linux 上建议 sudo 运行，或先执行 setcap 授权）
.venv/Scripts/python -m uvicorn app.main:app --app-dir backend --port 8000

# 3) 打开页面（首次会跳登录页；密码来源见下方「首次登录」）
#    登录          http://127.0.0.1:8000/login.html
#    监控大屏      http://127.0.0.1:8000/
#    流量监控      http://127.0.0.1:8000/traffic.html
#    威胁告警      http://127.0.0.1:8000/threat.html
#    封禁管理      http://127.0.0.1:8000/block.html
#    异常端口      http://127.0.0.1:8000/anomaly.html
#    规则管理      http://127.0.0.1:8000/rules.html
#    漏洞提醒      http://127.0.0.1:8000/vuln.html
#    资产管理      http://127.0.0.1:8000/asset.html
#    API 文档      http://127.0.0.1:8000/docs
```

**首次登录**：用户名 `admin`。若 `.env` 未设置 `ADMIN_INITIAL_PASSWORD`，启动日志会打印一次性随机密码
（`journalctl -u secops-traffic-guard | grep 一次性密码` 或开发终端日志）；登录后强制改密。
仅本地演示可临时设 `AUTH_ENABLED=false`，不要在生产使用。

Linux 上如需真实抓包与封禁：

```bash
sudo setcap cap_net_raw,cap_net_admin+eip $(readlink -f $(which python3))   # 免 root 抓包+封禁
# 或直接 sudo 启动服务
```

### 2.3 容器化一键部署

```bash
cd deploy
cp ../backend/.env.example .env
docker compose up -d --build
# 大屏 http://<服务器IP>:8080/dashboard/   （nginx 托管 + 反代 API，已关闭 SSE 缓冲）
```

裸机安装（含 systemd 服务、setcap、nginx 配置）：

```bash
sudo bash deploy/install.sh --with-nginx                  # 干跑模式（安全试用）
sudo bash deploy/install.sh --with-nginx --live-firewall   # 真正下发防火墙规则
```

## 3. 监控大屏（总览页）

**入口**：`/` 或 `/dashboard/`

### 3.1 页面构成

| 区域 | 内容 | 说明 |
| --- | --- | --- |
| 顶部 | 时钟 / 标题 / 状态徽标 | 「eBPF/libpcap/演示流量」= 采集模式；「iptables · DRY-RUN」= 防火墙后端与干跑状态 |
| 顶部右侧 | 告警音开关、立即扫描 | 告警音默认关闭（避免打扰）；立即扫描为异步任务 |
| 左列 | 实时核心指标、异常端口 TOP、事件类型分布 | 带宽利用率超 50% 变黄、超 80% 变红 |
| 中列 | 累计统计条、风险指数、实时趋势、攻击来源 TOP10、处置时间线 | 趋势图每 500ms 追加一帧 |
| 右列 | 风险 IP 封禁表（可解封）、实时告警播报（4s 轮转）、资产指纹/漏洞提醒切换 | 最新一条播报会高亮 |
| 左下角 | 模块导航 3.1~3.5 | 快速进入各模块页面 |

### 3.2 典型操作

1. **发现异常**：出现弹窗「恶意流量告警」，含事件类型、级别、源 IP、目标、检测算法、事件描述；
2. **研判**：弹窗中标注「已自动处置」表示系统已按策略封禁（DRY-RUN 下仅记录）；
3. **确认隔离**：点「确认隔离该 IP」→ 调用封禁接口 → 封禁表立即出现该 IP；
4. **纠错**：若属误报，到「封禁与告警」页点「解封」，或在异常端口页把该源加入白名单；
5. **静音**：点「告警音：关」（默认即关闭状态）。

> 若状态徽标显示「演示数据」或「实时连接中断，正在重连…」，说明后端不可达或 SSE 断开；
> 后端恢复后浏览器会**自动重连**，无需刷新页面。

## 4. 模块 3.1 实时动态流量监控（`traffic.html`）

### 4.1 指标含义

| 指标 | 含义 | 异常参考 |
| --- | --- | --- |
| 带宽利用率 | 当前总带宽 / `LINK_SPEED_MBPS` | > 50% 关注，> 80% 排查大流量或攻击 |
| 入站 / 出站带宽 | 双向实时速率（bps） | 出站远大于入站 → 疑似数据外泄 |
| 包速率 | 每秒数据包数（pps） | 小包高 pps → 扫描/洪泛特征 |
| 并发连接 | 连接表活跃会话数 | 突增 → 可能连接耗尽型攻击 |
| 活跃源 IP | 窗口内独立源地址数 | 突增 → 可能分布式扫描 |

### 4.2 可用操作

| 操作 | 位置 | 说明 |
| --- | --- | --- |
| 切换时间窗口 | 工具栏按钮组 | 最近 1 / 5 / 15 分钟（从内存环形缓冲回读历史） |
| 暂停画面 | 「暂停画面」 | 仅冻结图表追加，**后台采集与检测不受影响** |
| 导出会话 CSV | 「导出会话 CSV」 | 含源/目的、协议、时长、包数、字节、bps，便于离线分析 |
| 封禁可疑源 | 会话表「封禁源」 | 默认封禁 30 分钟，到期自动解封 |
| 查看数据源 | 面板头部提示 | 显示当前采集模式与网卡名 |

### 4.3 常见判断

* **表格中红色行**：目的地址不在内网（`192.168/10./172.16` 之外）的会话，多为外联行为，优先核对；
* **长时长 + 低速率会话**：到模块 3.1 的 TOP 会话中复核（连接仅作展示，不参与异常判定）；
* **导出后离线比对**：把 CSV 与历史同期基线对比，可快速定位异常联系。

## 5. 模块 3.2 异常端口流量检测（`anomaly.html`）

这是**检测能力的核心页**：把"端口级基线"与"异常事件"放在一起，做到"看到偏差就知道该不该处置"。

### 5.1 端口基线明细表（上半区）

| 列 | 含义 |
| --- | --- |
| 端口 / 协议 | 目的端口与服务协议 |
| 类型 | 标准端口（在 `STANDARD_PORTS` 之内）/ 非标准端口 |
| 当前 pps、当前带宽、连接数 | 最近 10 秒滑动窗口的实时值 |
| 基线均值 pps | EWMA 学习到的该端口"正常水平" |
| 偏离倍数 | 当前值 ÷ 基线均值 |
| Z 值 | 稳健 Z-score 偏离度；≥ 阈值（`ZSCORE_THRESHOLD`，默认 3.5）单元格变黄/红 |
| 主要来源 | 该端口流量最大的源 IP（处置按钮的作用目标） |
| 处置 | 「封禁」源 IP、「加白名单」（确认是误报时使用） |

**筛选**：全部端口 / 仅异常 / 仅非标准 + 端口号搜索；**导出 CSV** 便于留档。

三步判断法：

1. 看「类型」→ 非标准端口出现稳定高频访问，通常是后门、代理或 C2；
2. 看「偏离倍数」与「Z 值」→ 显著高于基线才是异常；缓慢增长往往只是业务量上升（此时不要封禁）；
3. 看「主要来源」→ 内部 IP 先内部核实，外部 IP 可直接封禁并保留证据。

### 5.2 异常事件列表（左下）

| 字段 | 说明 |
| --- | --- |
| 时间 / 类型 / 级别 | 发生时间、检测类别、严重级别（紧急/高危/中危/低危） |
| 源 IP / 端口 / 评分 | 攻击来源、命中端口、检测器自身的置信度评分（0~1，越高越确定） |
| 风险分（聚合） | 滑动窗口内的聚合风险分（权重累加 + 多类别/critical 加成），≥ 阈值才会告警 |
| 直达 | `直达` = 单条致命规则命中（立即告警）；`聚合` = 多条信号累计触发 |
| 状态 | 待处置 / 已封禁 / 已确认 |
| 操作 | 「详情」看完整证据与处置建议；「封禁」一键封禁源 IP；「确认」关闭告警 |

点「详情」打开右侧浮窗：事件描述、**AI 研判（来源/结论/置信度/建议 + 研判依据，可点「重新研判」）**、
**窗口 signals（聚合明细，直达告警窗口长度为 1）**、检测证据（`unique_dst_ports`、`port_entropy`、
`zscore`、`baseline_mean_pps` 等原始特征）、系统给出的**处置建议**。浮窗默认收起，只有点击「详情」才滑入，
可用 `×` / 点击遮罩 / `Esc` 关闭（统一交互见 1.5）。

### 5.3 阈值与信号（页面中部，v2 新增）

| 按钮 | 作用 |
| --- | --- |
| 阈值管理 | 打开抽屉：各维度当前阈值、静态基准、样本数、误报率、是否人工覆盖、最近更新时间 |
| 全部信号 / 仅被抑制 | 查看窗口内的 signal（含**未达阈值 / 冷却期被抑制**的，禁止静默丢弃） |
| 立即重算阈值 | 手动触发一次自适应阈值重算（等价于后台每 6 小时的定时任务） |
| 规则来源 | 打开抽屉：各来源（内置/Sigma/ET/扩展 CVE）规则数、HTTP 侧可用数、直达规则数与覆盖大类 |

### 5.4 事件类型占比（右下）

玫瑰图展示近 24 小时各类事件占比，可快速看出"哪种攻击在增多"，也便于写周报。

### 5.5 四类检测规则的判定口径

| 类别 | 判定逻辑（关键参数） | 典型场景 | 建议处置 |
| --- | --- | --- | --- |
| 非标准端口高频访问 `nonstandard_port` | 端口不在 `STANDARD_PORTS` 且 pps/连接数显著超基线（Z ≥ `ZSCORE_THRESHOLD`，默认 3.5） | 反弹 Shell、代理、C2 心跳 | 封禁 + 在目标机 `netstat -tunlp` 定位进程 |
| 端口扫描探测 `port_scan` | 单源 10s 内目的端口数 ≥ `PORT_SCAN_UNIQUE_PORTS`(60) 且端口熵 ≥ 3.0 | 资产发现、漏洞扫描器 | 外部源封禁；内部源核对是否合规扫描器 |
| 认证端口暴力破解 `brute_force` | 单源对 22/3389/3306 等端口访问次数 ≥ `BRUTE_FORCE_ATTEMPTS`(40) | SSH/RDP/DB 暴破 | 封禁 + 查登录日志、临时关闭密码登录 |
| 突发流量峰值 `traffic_spike` | 全局 bps ≥ 告警基线（`SPIKE_MIN_ABS_BPS`，默认 100Mbps）即起报：≥1.5× 基线且未达直达线给 high，其余给 medium（均走聚合窗口）；≥ `SPIKE_BPS_THRESHOLD`（默认 200Mbps）为 critical 直达 | DDoS、数据外泄、备份窗口 | 先确认业务窗口；非预期则限速/清洗并排查外联 |
| 多维行为异常 `behavior_anomaly` | 8 维行为向量被 Isolation Forest 判为离群 | 未知新型行为 | 人工复核，必要时提高该主机观察等级 |

### 5.6 AI 流量研判（v3）

页面中部工具栏 → **AI 流量研判**：把近 10 分钟的**聚合摘要**（bps/pps/连接数、端口 Top、
告警类别计数、未达阈值信号）交给模型，返回：

* 判定：正常 / 可疑 / 恶意 / 待定（含置信度）；
* 发现：窗口内按类别统计的告警与信号；
* 建议：封禁、核对日志、接口加固等可执行动作；
* 来源标签：`deepseek_v4_flash`（真实模型）或 `local_rules`（已降级，黄色标注）。

AI 结论**只作建议**：不会改变自动封禁判定（封禁仍由直达规则 + 严重度 + 白名单决定）。
对应接口：`GET /api/v1/ai/traffic/review?window_minutes=10`。

## 6. 封禁管理（`block.html`，原 `response.html`）

### 6.1 联动链路（页面顶部同步展示）

```
检测命中 → 白名单校验 → 防火墙下发（iptables/nftables/firewalld） → 落库审计 → 多通道通知
```

* 白名单校验命中 → 直接拒绝封禁，并在处置流水留痕（`success=false`）；
* 同一 IP 重复命中 → 只累加「命中次数」，不重复下发规则；
* 每条封禁都有 TTL，到期由后台线程自动解封（默认 30 分钟）。

### 6.2 手动封禁

填写「目标 IP/CIDR + 原因 + 时长」→「立即封禁」。支持 CIDR（如 `203.0.113.0/24`）。

返回语义化结果，便于判断为什么失败：

| 返回 code | 含义 |
| --- | --- |
| `ok` | 封禁成功（DRY-RUN 下表示已记录待生效） |
| `whitelisted` | 命中白名单，已拒绝封禁 |
| `duplicated` | 已在封禁中，仅累加命中次数 |
| `firewall_failed` | 防火墙下发失败（通常是权限不足或命令缺失） |

### 6.3 封禁表操作

| 操作 | 说明 |
| --- | --- |
| 续期 30 分 | 把到期时间再延后 30 分钟（攻击仍在持续时使用） |
| 解封 | 撤销防火墙规则 + 关闭相关告警 + 写入审计日志（误封纠错主入口） |
| 仅显示生效中 | 取消勾选可查看历史封禁全量记录 |
| 导出 CSV | 含 IP、类型、原因、操作人、时间、剩余时长、命中次数、DRY-RUN 标记 |

### 6.4 白名单（误报抑制）

| 场景 | 操作 |
| --- | --- |
| 内网巡检/漏洞扫描器被误判为扫描 | 添加扫描器 IP 或网段（如 `10.20.0.0/24`），备注"合规扫描器" |
| 办公网出口引发批量告警 | 添加出口 IP/网段，备注"办公出口" |
| 网关、堡垒机、监控节点 | 上线第一天就加入，避免被误封导致失联 |
| 内置项 | 回环、组播、链路本地地址为系统内置，不可删除 |

> **强烈建议**：启用 `DRY_RUN=false` 之前，先把网关、堡垒机、监控节点、运维办公网段加入白名单。

### 6.5 告警通道

* 通道列表显示当前生效通道：`log`（本地日志，始终启用）、`webhook:dingtalk`、`webhook:wecom`、
  `webhook:generic`、`email`、`syslog`；
* 点「发送测试告警」会向所有通道发一条 Markdown 测试消息，用于验证配置；
* 「最近发送记录」显示每条告警在各通道的成功/失败情况（失败会记录错误原因）。

配置方式（`.env`）：

```bash
ALERT_CHANNELS=log,webhook,email,syslog
DINGTALK_WEBHOOK=https://oapi.dingtalk.com/robot/send?access_token=xxx
WECOM_WEBHOOK=https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx
SMTP_HOST=smtp.example.com
SMTP_PORT=465
SMTP_USER=alert@example.com
SMTP_PASSWORD=********
SMTP_RECIPIENTS=secops@example.com,ops@example.com
SYSLOG_ADDRESS=siem.internal:514
```

### 6.6 处置时间线（审计）

记录每一次封禁/解封/白名单变更：时间、动作、目标、操作人、结果、详情（含实际执行的命令或失败原因）。
它是**事后追责与复盘**的依据，也是“为什么这个 IP 被封了”的直接答案。

### 6.7 安全事件报告（v6 P1）

封禁表每一行都有「生成报告」按钮，报告内容：

1. 摘要（事件数、告警数、最高级别、当前封禁状态）；
2. 封禁信息（原因、依据、下发方式、TTL、操作人、DRY-RUN）；
3. 攻击概览（类别/严重度/方向分布、时间跨度）；
4. 攻击时间线（按分钟）；
5. 代表性事件 Top 10；
6. 请求/响应证据（L0/L1/L2 显式标注，缺失不伪造）；
7. 影响评估（路径、Top 规则、研判分布；**不自动下“已失陷”结论**）；
8. 处置与建议（已执行动作、加固建议）；
9. 附录（告警列表、证据 SHA-256、生成时间）。

报告是自包含 HTML（内联 CSS、无外链），浏览器「打印 → 另存为 PDF」即可归档；
文件默认落 `backend/data/reports/`（首次生成报告时自动创建），可用 `REPORT_DIR` 调整。

## 7. 模块 3.4 漏洞提醒与修复建议（`vuln.html`）

### 7.1 流程

```
资产指纹识别（nmap -sV 优先，banner 抓取兜底）
  → 匹配 CVE 知识库（backend/data/cve_rules.json，内置 18 条规则）
  → Web 应用只读体检（WEB-001~011：响应头/Cookie/暴露面/演示页…）
  → 攻击流量研判（用已捕获的请求+响应判断注入/上传/包含是否打穿，见 7.8）
  → 生成修复建议与最低修复版本
  → 人工推进状态：待修复 → 修复中 → 已修复 / 已忽略
```

> 三条来源各自看不到对方的盲区：CVE 匹配只看版本、Web 体检只看配置与暴露面，
> 而注入类漏洞**没有版本特征**，只有"被打过且响应回显了结果"才判得出来。

### 7.2 清单字段与操作

| 列 | 含义 |
| --- | --- |
| CVE | 漏洞编号：`CVE-*` 来自版本匹配，`WEB-*` 来自 Web 体检，`CWE-*` 来自攻击流量研判（如 `CWE-78` 命令注入） |
| 漏洞标题 | 漏洞简述 |
| 主机:端口 | 受影响资产与端口 |
| 服务/版本 | 指纹识别出的产品与版本 |
| CVSS / 级别 | 危险评分与等级（≥9 红色、≥7 橙色） |
| 状态 | 待修复 / 修复中 / 已修复 / 已忽略 |
| 操作 | 「建议」查看修复方案；「修复中 / 已修复 / 忽略」推进状态 |

其他按钮：严重级/状态筛选、关键字搜索（CVE/标题/主机）、「查看知识库」、「导出 CSV」。

### 7.3 主动扫描（异步任务）

点「立即扫描」后：

1. 后端立即返回任务号（`scan-N`），**不会**让浏览器长时间等待（避免网关超时导致 500）；
2. 按钮显示实时进度 `扫描中 xx%`；
3. 下方「扫描任务」表展示任务号、状态、进度、目标数、发现服务数、发现漏洞数、耗时；
4. 完成后自动刷新漏洞清单与统计。

扫描目标默认取"已发现的资产"，也可用 `SCAN_TARGETS=192.168.1.0/24` 指定网段（上限 256 个地址）。

### 7.4 修复建议抽屉

包含：漏洞描述、严重级别与 CVSS、影响主机与端口、当前状态、**修复建议**（可直接执行的升级/配置动作）、
最低修复版本、检测证据（例如「识别到 OpenSSH 8.2（端口 22），低于修复版本 9.3p2」）。

浮窗默认收起，只有点击该行的「建议」按钮才滑入；关闭方式与其它模块一致（`×` / 点遮罩 / `Esc`，见 1.5）。

### 7.5 扩展知识库（无需改代码）

编辑 `backend/data/cve_rules.json` 新增规则即可：

```json
{
  "cve": "CVE-2025-XXXXX",
  "title": "某中间件远程代码执行",
  "product_regex": "myproduct",
  "version_lt": "2.4.0",
  "severity": "critical",
  "cvss": 9.8,
  "fixed_version": "2.4.0",
  "recommendation": "升级至 2.4.0 及以上；临时缓解可关闭 xx 功能。"
}
```

支持字段：`product_regex` / `service_regex`、`ports`、`banner_regex`、
`version_lt/le/gt/ge/eq`、`version_between`。改完重启服务生效。

### 7.6 Web 业务站点漏扫（通用）

工具栏输入站点地址（如 `http://127.0.0.1:8080/`）→ **Web 漏扫**：

1. **指纹**：记录页面标题、`Server`、`X-Powered-By`、是否登录成功、爬取页数，
   不依赖任何产品名（换业务系统照样可用）；
2. **登录（可选）**：页面存在密码表单且配置了 `WEBAPP_SCAN_USERNAME` /
   `WEBAPP_SCAN_PASSWORD` 时提交一次登录；系统不内置任何默认口令；
3. **只读检查 11 项**：安全响应头、Cookie 属性、版本泄露、目录列举、敏感文件、
   安装脚本、危险 HTTP 方法、错误页泄露、管理入口、演示页、明文 HTTP
   （编号 `WEB-001`~`WEB-011`），每项都要「状态码 + 内容标记」同时命中才落库；
4. **有界爬取**：只跟同主机链接，默认 ≤24 页 / ≤20 秒，跳过登出与静态资源；
5. **CVE 匹配**：仅当 `Server`/`X-Powered-By` 解析出版本号时按区间匹配
   （Apache / Nginx / PHP）。

所有记录都带 `GET <url> 返回 HTTP 200，命中...` 的证据，可在「建议」抽屉里复核。
未配置扫描凭据时只扫匿名可见面，不会猜测登录后的漏洞。

### 7.7 AI 修复建议（v3）

漏洞行 **AI 建议**（或详情抽屉「生成 / 重新生成 AI 建议」）→ 返回：

* `summary`：风险摘要；`steps`：3~6 条可执行步骤（含备份/回滚/变更窗口）；
* `verification`：修复后的验证方法；`risk`：高/中/低；
* `source`：`deepseek_v4_flash` 或 `knowledge_base`（已降级，黄色标注）。

接口：`POST /api/v1/vulns/{id}/ai-advice`；结果写入漏洞记录的 `ai_advice` / `ai_source`，
下次打开详情直接展示。

---

### 7.8 按攻击流量研判漏洞（补主动漏扫的盲区）

主动漏扫只能看端口、版本、配置和暴露面；命令注入、SQL 注入、文件包含、XSS、上传这类
**应用逻辑缺陷没有版本指纹**，站点跑得再正常也扫不出来。系统用第三条路径补上：

1. **素材**：检测到 Web 攻击时落库的 `threat_events`（方法、路径、查询串、请求体、响应头、响应体）；
2. **规则研判**：先看响应里有没有客观证据——
   * 命令回显（`uid=33(www-data)` 这类执行结果）→ 命令注入；
   * 数据库报错特征 → SQL 注入；
   * `/etc/passwd` 的特征行 → 文件包含 / 目录穿越；
   * 载荷被原样反射进 HTML → 反射型 XSS；
   * 命中拦截页 → 直接判定不成立（避免把 WAF 拦截当成打穿）；
3. **AI 复核**：模型可以把"疑似"升为"确认"、也可以否定纯特征猜测，但**不能推翻响应里的客观证据**；
4. **结论**：`已确认`（响应有证据）/ `疑似`（只有请求特征，或没抓到响应包），写入漏洞表，
   来源标注 `攻击流量·规则研判` 或 `攻击流量·AI 复核`。

**通用性**：漏洞名只取技术类型（`命令注入`、`CWE-78`），不含任何产品名、站点名或靶场名——
同样的结论可以来自任何一套业务系统。

**触发方式**：

* 自动：检测链路命中 Web 攻击后立即研判一次（只跑规则，不调模型，按 `ip:port` 30 秒节流）；
* 手动：资产详情抽屉 →「按攻击流量研判漏洞」（带 AI 复核，`POST /assets/{ip}/vuln-infer`）。

**关于"0 条结果"**：说明该资产要么还没被打过，要么采集等级不够——`log` 模式只有访问日志、
没有响应体，因此只能记「疑似」；需要「已确认」请用代理模式（`--http-proxy`）或 WAF 投递完整请求与响应。

## 8. Web 攻击检测（HTTP 侧）

第七章的 CVE 知识库回答「资产存在哪些已知漏洞」，本章回答「**流量里正在发生什么 Web 攻击**」——
两者共用同一套告警、自动封禁与通知链路（告警类别形如 `web_sql_injection`）。

### 8.1 检测能力（知识库：`backend/data/web_attack_rules.json`）

| 攻击大类 | OWASP / CWE | Web 业务 对照模块 | 典型载荷 |
| --- | --- | --- | --- |
| SQL 注入 | A03 / CWE-89 | SQL Injection | `?id=1' OR '1'='1`、`union select`、`extractvalue(` |
| SQL 盲注 | A03 / CWE-89 | SQL Injection (Blind) | `AND SLEEP(5)`、`ASCII(SUBSTRING(...))`、`WAITFOR DELAY` |
| 反射型 XSS | A03 / CWE-79 | XSS (Reflected) | `<script>alert(1)</script>`、`<img src=x onerror=...>` |
| 存储型 XSS | A03 / CWE-79 | XSS (Stored) | 留言/昵称字段提交 `<script>`、`<svg/onload=...>` |
| 命令注入 | A03 / CWE-78 | Command Injection | `;cat /etc/passwd`、`\|whoami`、`$(...)`、反弹 Shell |
| 文件包含 | A03 / CWE-98 | File Inclusion | `?page=../../../../etc/passwd`、`php://filter/`、`http://evil/x.txt` |
| 恶意文件上传 | A04 / CWE-434 | File Upload | `filename="shell.php"`、双扩展名、上传内容含 PHP 木马特征 |
| 暴力破解 | A07 / CWE-307 | Brute Force | 60 秒内同一来源 ≥10 次登录尝试（阈值可配） |
| CSRF | A01 / CWE-352 | CSRF | 状态变更请求缺少 Token，且缺少 Origin/Referer |
| 不安全验证码 | A07 / CWE-804 | Insecure CAPTCHA | `captcha=` 空值或固定值、`step=2` 跳步、验证码接口高频拉取 |
| 目录穿越 | A01 / CWE-22 | File Download | `../../../../etc/shadow`、`%2e%2e%2f`、`.git/config` |
| SSRF | A10 / CWE-918 | SSRF | `url=http://169.254.169.254/latest/meta-data/`、`gopher://`、`@127.0.0.1` |
| XXE | A05 / CWE-611 | XXE | `<!DOCTYPE ... SYSTEM "file:///etc/passwd">`、参数实体外带 |
| Webshell 访问 | A03 / CWE-506 | File Upload | `/upload/shell.php?cmd=whoami`、一句话木马特征 |
| 服务端模板注入 | A03 / CWE-1336 | SSTI | `{{7*7}}`、`{{config.__class__.__init__.__globals__}}`、`${T(java.lang.Runtime)...}` |
| LDAP/NoSQL 注入 | A03 / CWE-90 | LDAP/NoSQL Injection | `user=*)(uid=*))(\|(uid=*`、`username[$ne]=x` |
| CRLF 注入 | A03 / CWE-93 | CRLF Injection | `next=%0d%0aSet-Cookie:admin=1` |

判定细节（既防漏报也防误报）：

1. **先归一化再匹配**：多轮 URL 解码 → HTML 实体解码 → SQL 注释（`/**/`）转空格 → 空白折叠 → 转小写，
   因此 `%2527`、`UNION/**/SELECT`、`&lt;script&gt;` 都会被还原后命中；
2. **多字段匹配**：路径、查询串、请求体、请求头、Cookie、上传文件名分别匹配，命中字段会写入告警证据；
3. **频次阈值**：暴力破解 / CSRF / 验证码类规则按「窗口内累计次数」判定，单次访问不会告警；
4. **误报抑制**：带 CSRF Token 的请求、登录认证端点、正常业务关键词都不会触发；
5. **组合攻击提级**：同一请求命中多类攻击时自动提级（如中危 → 高危），文案标注「组合攻击」。

### 8.2 数据来源（`WEB_DETECT_SOURCE`）

| 模式 | 适用场景 | 说明 |
| --- | --- | --- |
| `demo`（默认，未配置日志时自动使用） | 演示 / 联调 | Web 业务 风格仿真请求，覆盖全部 17 类，开箱即见告警 |
| `log` | 生产推荐（零侵入） | tail nginx/Apache combined 访问日志，只读且从文件末尾开始；弱点是看不到请求体，存储型 XSS / 上传载荷类规则不会触发 |
| `api` | 已有 WAF / 反向代理 | 由外部通过 `POST /web/requests` 投递完整请求（可见 body / headers）；内置 Web 业务 高保真代理见 `--http-proxy` |
| `off` | 关闭 | 仅保留流量侧检测 |

### 8.3 页面与接口

* 「漏洞提醒」页：KPI「Web 攻击规则数」+「Web 攻击规则」按钮（知识库抽屉：17 类卡片 + 规则明细表，含 CWE/OWASP/置信度/命中示例）；
* 「异常端口检测」页：KPI「Web 攻击告警」，告警列表类型列显示「Web-SQL 注入」等中文名，
  详情抽屉展示命中片段、规则编号、CWE、修复建议，并可一键封禁来源 IP；
* 接口速查：

```bash
# 知识库概览 / 单个大类
curl -s http://127.0.0.1:8000/api/v1/web/kb | head -c 400
curl -s http://127.0.0.1:8000/api/v1/web/kb/sql_injection
# 运行统计（已分析请求数、各大类命中数、数据来源）
curl -s http://127.0.0.1:8000/api/v1/web/stats
# 单条请求体检（只检测、不告警，用于规则自测与 WAF 联调）
curl -s -X POST http://127.0.0.1:8000/api/v1/web/inspect -H 'Content-Type: application/json' \
  -d '{"method":"GET","path":"/app/demo/sqli/","query":"id=1%27+OR+%271%27%3D%271"}'
# 批量投递（走完整检测 → 告警 → 封禁闭环）
curl -s -X POST http://127.0.0.1:8000/api/v1/web/requests -H 'Content-Type: application/json' \
  -d '{"requests":[{"method":"POST","path":"/upload","body":"filename=\"shell.php\""}]}'
```

### 8.4 扩展规则（无需改代码）

编辑 `backend/data/web_attack_rules.json` 的 `rules` 数组即可，字段含义见文件内 `field_help`：

```json
{
  "id": "WEB-CUSTOM-001",
  "category": "sql_injection",
  "title": "自研业务：订单查询接口注入特征",
  "severity": "high",
  "cvss": 8.5,
  "confidence": "medium",
  "match_targets": ["query", "body"],
  "patterns": ["order_id\\s*=\\s*\\d+\\s*(or|union)"],
  "exclude_patterns": ["/internal/report"],
  "threshold": { "window_sec": 60, "count": 2 },
  "remediation": "该接口改用参数化查询，并对 order_id 做纯数字校验。",
  "references": ["https://owasp.org/Top10/A03_2021-Injection/"],
  "examples": ["?order_id=1 or 1=1"]
}
```

要点：`category` 必须是 `categories` 里已存在的大类（也可自行新增大类）；新增规则后重启服务，
或调用 `POST /rules/reload` 热加载（无需重启）。

### 8.5 规则来源层（v2：内置知识库 + 开源规则库）

| 来源 | 文件 | 加载策略 |
| --- | --- | --- |
| `native` | `data/web_attack_rules.json`、`data/cve_rules.json` | 内置知识库；命令注入/Webshell/SSTI/文件上传/XXE(高置信度) 自动标记为**直达规则** |
| `sigma` | `data/sigma_rules/*.yml` | 只保留能在流量侧匹配的规则（webserver/proxy，或 detection 字段能映射到 HTTP 字段）；进程创建、注册表、文件系统类**跳过并计数** |
| `et` | `data/et_rules/*.rules` | 只解析入向 `http` 的 `alert` 行；`flow:...to_client`、含十六进制字节块的 content 跳过 |
| `cve_ext` | `data/cve_rules_extended.json` | 与内置 CVE 合并（同编号以扩展为准）；CVE 规则**永不直达**（版本匹配存在不确定性） |
| `intrusion` | `data/rulesets/intrusion_rules.json` | 742 条（HTTP 633 + 流级 109）；按 `core/extended/lab` 分档，默认只装 core 的 HTTP 部分 |
| `triage` | `data/rulesets/triage_rules.json` | 300 条研判条件；`TRIAGE_ENABLED=true` 时在聚合前执行，只抑制/调分，不直接封禁 |
| `malware` | `data/rulesets/malware_signatures.json` | 329 条病毒特征；文件扫描执行器后续批次，默认关闭 |

* 规则包开关：`RULESETS_ENABLED` / `RULES_TIERS` / `RULES_SHADOW_MODE`；未定义类别默认**拒绝加载并报错**；

* 开关：`SIGMA_RULES_ENABLED` / `ET_RULES_ENABLED` / `CVE_EXT_ENABLED`（关闭即回落到仅内置知识库）；
* 查看：`GET /rules/sources`（各来源规则数/直达数）、`GET /rules?source=sigma&direct_only=true`；
* 热加载：`POST /rules/reload`，或 `RULE_RELOAD_INTERVAL_SEC`（默认 300s）自动重载；
* 启动日志会打印 `rules loaded: native=…, sigma=…, et=…, cve_ext=…, direct_alert=…`。

### 8.6 评分与直达机制（v2：告警不再逐条轰炸）

```
命中规则 → signal（权重 = 严重度 × 置信度）
             ├─ 直达：weight ≥ DIRECT_ALERT_WEIGHT(6.0) 或规则被标记 direct_alert → 立即告警
             └─ 聚合：进入该源 IP 的 300s 滑动窗口，风险分 ≥ ALERT_SCORE_THRESHOLD(6.0) 才告警
                        （≥2 类 ×1.2，≥3 类 ×1.5，窗口内存在 critical 时 ×1.3）
冷却期（ALERT_COOLDOWN_SEC）内重复触发只记录为"被抑制的信号"，不重复告警
```

* 权重表：critical 5.0 / high 3.0 / medium 1.5 / low 0.5，置信度系数 high 1.2 / medium 1.0 / low 0.8；
  因此 **critical + high = 6.0 恰好等于直达阈值**（"单条致命且高置信度"才直达）；
* **不改变自动封禁门槛**：`AUTO_BLOCK_*` 仍是唯一封禁入口，评分只影响告警的展示与排序；
* 未达阈值 / 被冷却抑制的 signal **同样落库**，可在「阈值与信号」表格或 `GET /signals?suppressed_only=true` 查看；
* 查看当前配置与运行统计：`GET /scoring/config`。

### 8.7 自适应阈值（v2：让阈值跟着误报反馈走）

* 维度：`检测类型 × 资产口径 × 时段`（例如 `port_scan × 服务器 × 工作时间`）；
* 反馈来源：告警被**封禁** = 真阳；被**确认关闭** = 误报；仍 `open` 的告警不计入；
* 调整规则：误报率 > `THRESHOLD_FP_HIGH`(0.5) → 阈值 ×1.3 收紧；< `THRESHOLD_FP_LOW`(0.1) → ×0.9 放松；
  结果被限制在静态基准的 `0.5~2.0` 倍内，且要求 ≥5 个已处置样本；
* 人工覆盖：`PATCH /thresholds/{id}` 后该维度被标记 `manual_override`，自动重算会**跳过**它；
* **直达机制不参与本机制**（规则固有属性，避免削弱对致命攻击的响应能力）；
* 定时任务每 `THRESHOLD_RECOMPUTE_INTERVAL_SEC`(6h) 重算一次，也可在页面点「立即重算阈值」。

### 8.8 AI 研判与降级链（v2：结论来源永远标注）

一级一级往下退，**每一级都在前端标注来源**，绝不让"降级"被静默：

| 顺序 | 来源标签 | 触发条件 | 颜色 |
| --- | --- | --- | --- |
| 1 | DeepSeek V4-Flash | `LLM_ENABLED=true` 且配置 `LLM_API_KEY`，调用成功且输出通过 schema 校验 | 绿 |
| 2 | 本地规则判定 | API 不可用，但聚合风险分 ≥ 阈值 ×1.5 或命中直达规则（证据已充分） | 黄 |
| 3 | 静态模板 | API 不可用，且该攻击大类有预设模板 | 灰 |
| 4 | 待人工研判 | 以上都不适用 | 红 |

* 安全约束：**只发送结构化摘要**（类别/级别/评分/规则 ID/证据数值），内网 IP 默认脱敏，
  原始 URL、payload、User-Agent **绝不外发**（防 Prompt 注入）；
* 异步执行：研判在后台线程完成，不阻塞 500ms 的采集/检测节奏；完成后通过 SSE `alert_enriched` 事件回推前端；
* 手动触发：告警详情「重新研判」按钮 → `POST /alerts/{alert_id}/reanalyze`；
* 结果字段：`source`（来源）、`verdict`（confirm/suspect/dismiss/unknown）、`confidence`、`suggestion`、
  `reason`、`evidence_refs`、`degraded`。

### 8.9 通用 Web 模式与防误报（v3）

高置信直达规则默认加载 `backend/data/web_strict_rules.json`（8 条，与产品/路径无关）：

* **载荷特征**：只看攻击载荷本身，不限定业务路径与产品——UNION/SLEEP、
  `;cat /etc/passwd`、`../../../../etc/passwd`、`filename="shell.php"` 这类形状
  正常业务参数不会出现，因此换任何业务系统都能识别；
* **直达**：命中即 `direct_alert=true`，绕过聚合投票立即告警，并可自动封禁；
* **暴破阈值**：登录接口 60s 内 ≥ `WEB_BRUTE_FORCE_ATTEMPTS`(10) 次才告警。

> **POST body 与高保真接入**：Apache combined 日志没有请求体，因此命令注入
> （`ip=127.0.0.1;cat /etc/passwd`）与文件上传（`filename=shell.php`）在 `WEB_DETECT_SOURCE=log`
> 下不会命中。使用 `sudo bash deploy/install.sh --http-proxy` 让内置代理占用 8080、Apache 退到
> 8081，代理在转发的同时把完整请求投递到 `POST /web/requests`，即可覆盖全部 Web 攻击。
> 来源 IP 取自 `X-Forwarded-For`，自动封禁仍作用于攻击机。

配套的防误报开关：

| 开关 | 作用 |
| --- | --- |
| `WEB_IGNORE_IPS` | 忽略指定来源（管理机/扫描器），不计入 Web 检测 |
| `WEB_AUTO_BLOCK_REQUIRES_DIRECT=true` | Web 告警自动封禁必须由直达规则确认 |
| `DETECT_IGNORE_IPS` | 流量统计忽略本机/授权扫描器（如 `127.0.0.1`，避免自扫描触发端口扫描） |
| `IFOREST_ENABLED=false`（靶场模板） | 关闭无监督离群告警，避免 ~5% 固有离群率造成"误报"观感 |
| `CVE assume_risk_if_unknown=false` | 版本未知时不猜 CVE |

### 9.3 统计图与使用建议

* 风险等级分布饼图：一眼看出多少资产处于高危/紧急；

* 对"开放端口多 + 漏洞多 + 告警多"的资产优先加固。

## 10. 日常运维手册

### 10.1 每日巡检（5 分钟）

```text
1) 打开监控大屏：状态徽标是否为 eBPF/libpcap（而不是"演示数据"）？
2) 「封禁中 IP」数量是否异常增长？（骤增说明攻击活动频繁）
3) 「待修复漏洞」是否有新增 critical？
4) 异常端口页：是否有连续多条同类告警指向同一源？（考虑延长封禁 TTL）
```

### 10.2 每周巡检（30 分钟）

```bash
# 告警复盘：按类型/级别/来源统计
curl -s http://127.0.0.1:8000/api/v1/alerts/stats?hours=168 | jq

# 检查是否存在"长期封禁"（>24h）需要复核
curl -s 'http://127.0.0.1:8000/api/v1/blocks?active_only=true&limit=200' \
  | jq '.items[] | select(.remaining_sec > 86400)'

# 资产与漏洞导出留档
curl -s http://127.0.0.1:8000/api/v1/assets?limit=1000   > assets.json
curl -s 'http://127.0.0.1:8000/api/v1/vulns?status=open'  > vulns-open.json

# 触发一次全量扫描并跟踪任务进度
curl -s -X POST http://127.0.0.1:8000/api/v1/vulns/scan \
     -H 'Content-Type: application/json' -d '{}' | jq
curl -s http://127.0.0.1:8000/api/v1/vulns/scan/jobs | jq '.items[0]'
```

### 10.3 每月巡检（半天）

* **阈值标定**：复盘 `/alerts/stats`，若某类告警绝大多数被"确认关闭"（误报），适当调高阈值：
  `ZSCORE_THRESHOLD`、`PORT_SCAN_UNIQUE_PORTS`、`BRUTE_FORCE_ATTEMPTS`、`SPIKE_BPS_THRESHOLD`；
* **白名单梳理**：删除已下线设备的白名单条目，避免形成盲区；
* **漏洞推进**：确保 critical 漏洞已进入修复流程，逾期未修复的升级通报；
* **容量检查**：数据库体积（`data/secops.db` 或 PostgreSQL）、InfluxDB 保留策略、日志轮转。

### 10.4 应急处理流程

| 场景 | 立即动作 | 后续动作 |
| --- | --- | --- |
| 主机正在被暴破 | 异常端口页找到该事件 →「封禁」源 IP（或续期至 1 天） | 检查登录日志，临时关闭密码登录/开启 NLA；通知主机负责人 |
| 出现大量突发流量 | 流量监控页确认是入站还是出站 | 入站 → 边界限速/清洗；出站 → 定位外联进程，必要时断网取证 |
| 非标准端口出现稳定流量 | 异常端口页记下端口与来源 →「封禁」 | 目标机 `netstat -tunlp \| grep <port>` 定位进程，排查后门 |
| 误封造成业务中断 | 封禁与告警页 →「解封」 | 加入白名单 + 调优阈值，避免同类误报 |
| 告警通道没收到通知 | 封禁与告警页「发送测试告警」看失败原因 | 检查 Webhook token / SMTP 配置 / 网络可达性 |

## 11. 常见问题（FAQ）

| 问题 | 原因与解决 |
| --- | --- |
| 页面右上角显示「演示数据」 | 后端不可达。检查服务是否启动、端口是否被拦截；若以 `file://` 打开，需保证后端在 `127.0.0.1:8000`，或用 `?api=http://<ip>:8000/api/v1` 指定 API 地址 |
| 大屏图表不动 | SSE 被代理缓冲。nginx 需配置 `proxy_buffering off;` 与 `X-Accel-Buffering no`（本项目已提供配置）；IE 等老浏览器不支持 EventSource |
| 刷新后图表错位 / 挤在一起，缩放窗口才恢复 | 已修复（v1.3）：图表容器是 rem 单位，旧代码在设置 rem 基准之前就 `echarts.init()`，把错误尺寸固化进了画布。现在 CSS 兜底 `html{font-size:calc(100vw/22)}` + 各页先定基准再初始化 + `ResizeObserver` 自动跟随。若仍复现，请强制刷新（Ctrl+F5）清掉旧 JS/CSS 缓存 |
| 采不到真实流量（一直演示） | Linux 下无权限 → root 运行或 `setcap cap_net_raw,cap_net_admin+eip <python>`；容器内需 `cap_add: NET_RAW`，抓宿主机流量还需 host 网络 |
| 封禁显示成功但 `iptables -L` 没有规则 | 当前为 DRY-RUN 模式（`DRY_RUN=true`），只记录不生效。确认无误后改 `false` 并重启 |
| 某 IP 死活封不上 | 命中白名单（返回 `code=whitelisted`）。到「白名单」面板确认是否包含它或其所在网段 |
| 告警太多 / 太少 | 多 → 提高 `ZSCORE_THRESHOLD`、`SPIKE_BPS_THRESHOLD`，或加大 `ALERT_COOLDOWN_SEC`；少 → 降低阈值、缩短 `ANOMALY_WARMUP_TICKS` |
| 点扫描没反应 | 扫描是**后台任务**，请在「扫描任务」表查看进度；未安装 nmap 时会用 banner 抓取（较慢但可用） |
| 漏洞列表是空的 | 需要先有资产（被动学习需运行一段时间，或手动触发扫描）；知识库只覆盖内置规则范围 |
| 资产页一直是空 | 被动学习只记录**内网**主机的服务端口访问；若流量都发往外部，请配置 `SCAN_TARGETS` 主动扫描发现 |
| 重启后封禁规则丢了 | 只记录在数据库、不会自动重放下发（设计如此，避免重启误伤）。可在页面重新封禁，或按审计流水核对 |
| 一条 Web 攻击告警都没有 | 1) 确认 `WEB_DETECT_ENABLED=true`；2) `WEB_DETECT_SOURCE=log` 时检查 `WEB_LOG_PATH` 是否存在且持续有新日志（也可以先用 `auto`/`demo` 验证链路）；3) `log` 模式看不到请求体，存储型 XSS/上传类规则本来就不会命中——需要完整请求时改用 `api` 模式由 WAF/代理投递 |
| Web 攻击告警太多（误报） | 提高 `WEB_BRUTE_FORCE_ATTEMPTS`、延长 `ALERT_COOLDOWN_SEC`；把可信来源（压测机、扫描器、巡检平台）加入白名单；对特定接口在知识库里补 `exclude_patterns` |
| 想自己加 Web 攻击规则 | 编辑 `backend/data/web_attack_rules.json` 的 `rules` 数组（`patterns`/`match_targets`/`threshold`/`exclude_patterns`），`POST /rules/reload` 热加载后 `GET /web/kb` 看 `stats.rules` 是否变化；字段含义见文件内 `field_help`，详见第 8.4 节 |
| 想让系统用开源规则集（Sigma / Suricata） | 把规则文件放进 `backend/data/sigma_rules/`（`*.yml`）或 `backend/data/et_rules/`（`*.rules`），`POST /rules/reload` 或等 5 分钟自动加载；`GET /rules/sources` 可看到各来源命中条数与跳过原因（进程/注册表类规则会被跳过） |
| 告警数量比之前少了 | 这是 v2 的预期行为：单条中低风险命中不再逐条告警，而是在 300s 窗口内累计到风险分阈值才告警；请通过「阈值与信号」表格确认信号仍在（未被静默丢弃），或用 `GET /alerts/stats` 的 `signals.suppressed` 观察抑制量 |
| 想让某类高危攻击"一命中就告警" | 该类规则需被标记为直达（`direct_alert`）：内置知识库中命令注入/Webshell/SSTI/文件上传/XXE 已自动直达；自研规则可在规则里加 `"direct_alert": true`，或把 `DIRECT_ALERT_WEIGHT` 调低于该规则权重（权重 = 严重度 × 置信度） |
| AI 研判一直显示"静态模板/待人工" | 正常降级：未配置 `LLM_API_KEY`、或 API 不可达/超时/返回非法 JSON 都会降级（阈值 3s，最多重试 1 次）。填入 `LLM_API_KEY` 后点「重新研判」即可验证；降级来源与原因都写在 `llm_analysis.source` / `degraded` 里 |
| 升级后报错"no such column: xxx" | 正常情况下**不会出现**：服务启动会自动补列（只加列不删改）。若仍报错，说明自动补列被跳过（权限不足等），停服后执行 `python scripts/migrate_v2.py` 手工补齐（幂等；加 `--dry-run` 先看要执行什么 SQL） |
| 阈值被系统自动改了 | 自适应阈值按误报率收放（幅度限制在静态基准 0.5~2.0 倍）。希望固定阈值时设 `ADAPTIVE_THRESHOLD_ENABLED=false`，或对某维度用 `PATCH /thresholds/{id}` 做人工覆盖（覆盖后自动重算会跳过它） |

## 12. 常用 API 速查（自动化/对接用）

> 开启登录后，除 `/health`、`/auth/login` 外的接口都需要会话 Cookie 或 `X-API-Token`。
> 下面的 `curl` 以机器调用为例，请先在 `.env` 设置非空 `API_TOKEN`：
> `AUTH="X-API-Token: $API_TOKEN"`，并给每条命令加 `-H "$AUTH"`。

```bash
BASE=http://127.0.0.1:8000/api/v1
AUTH="X-API-Token: ${API_TOKEN}"

# 健康与状态
curl -s $BASE/health | jq                 # 公开：采集模式、防火墙后端、DRY-RUN、通道
curl -s -H "$AUTH" $BASE/status | jq      # 运行状态（tick 数、连接表、ML 模型就绪等）

# 指标（模块 3.1）
curl -s "$BASE/metrics/trend?window_sec=300" | jq '.bps_in[-5:]'
curl -s "$BASE/metrics/sessions?top=20" | jq '.items[0]'
curl -s "$BASE/metrics/ports?top=10" | jq

# 异常检测（模块 3.2）
curl -s "$BASE/metrics/ports/baseline" | jq '[.items[] | select(.anomaly)]'
curl -s "$BASE/alerts?limit=20" | jq '.[] | {category, severity, source_ip, message}'
curl -s "$BASE/alerts/stats?hours=24" | jq
curl -s "$BASE/alerts/1" | jq '.suggestion'

# 封禁与告警（模块 3.3）
curl -s -X POST $BASE/blocks -H 'Content-Type: application/json' \
     -d '{"ip":"203.0.113.66","reason":"扫描来源","ttl_sec":1800}' | jq
curl -s -X POST "$BASE/blocks/203.0.113.66/extend?ttl_sec=3600" | jq
curl -s -X DELETE $BASE/blocks/203.0.113.66 | jq
curl -s "$BASE/disposals?limit=20" | jq '.items[0]'
curl -s -X POST $BASE/notify/test | jq

# 漏洞与资产（模块 3.4 / 3.5）
curl -s -X POST $BASE/vulns/scan -H 'Content-Type: application/json' -d '{}' | jq
curl -s $BASE/vulns/scan/jobs | jq '.items[0]'
curl -s "$BASE/vulns?status=open" | jq '.[] | {cve, asset_ip, port, fixed_version}'
curl -s -X PATCH "$BASE/vulns/3?status=fixed" | jq
curl -s $BASE/assets | jq '.[0]'
curl -s -X POST "$BASE/assets/192.168.1.10/rescan?use_nmap=true" | jq

# 白名单
curl -s -X POST $BASE/whitelist -H 'Content-Type: application/json' \
     -d '{"cidr":"10.20.0.0/24","note":"办公网段"}' | jq
curl -s -X DELETE $BASE/whitelist/10.20.0.0/24 | jq

# 实时流（SSE，Ctrl+C 退出）
curl -N $BASE/stream/metrics            # 指标帧
curl -N $BASE/stream/events             # alert / alert_enriched / signal 三类事件

# 统一规则层（v2）
curl -s $BASE/rules/sources | jq '.sources[] | {source, rules, direct_alert}'
curl -s "$BASE/rules?source=sigma&direct_only=true" | jq '.items[0]'
curl -s -X POST $BASE/rules/reload | jq '.message'

# 评分与信号（v2）
curl -s $BASE/scoring/config | jq '{threshold, direct_alert_weight, window_sec, note}'
curl -s "$BASE/alerts?direct_only=true&min_score=6&limit=10" | jq '.[0] | {category, risk_score, contributing_rules}'
curl -s "$BASE/signals?suppressed_only=true&limit=10" | jq '.[0]'
curl -s "$BASE/signals/window/203.0.113.66" | jq

# 自适应阈值（v2）
curl -s $BASE/thresholds | jq '.items[] | {detection_type, asset_class, threshold_value, false_positive_rate}'
curl -s -X POST $BASE/thresholds/recompute | jq '.message'
curl -s -X PATCH $BASE/thresholds/1 -H 'Content-Type: application/json' \
     -d '{"threshold_value":8,"reason":"业务确认"}' | jq

# AI 研判（v2）
curl -s -X POST $BASE/alerts/1/reanalyze | jq '.detail.analysis | {source, verdict, degraded, reason}'
```

> 若设置了 `API_TOKEN`，所有写接口（POST/DELETE/PATCH）需追加 `-H "X-API-Token: <token>"`。

## 13. 常用参数速查（`.env`）

| 参数 | 默认 | 什么时候改 |
| --- | --- | --- |
| `DRY_RUN` | `true` | 验证无误、确认白名单后改 `false`，让封禁真正生效 |
| `CAPTURE_MODE` | `auto` | 强制指定：`ebpf`（性能最好）、`scapy`（兼容最好）、`demo`（演示） |
| `TICK_INTERVAL_MS` | `500` | 追求更高实时性改小（250）；主机负载高改大（1000） |
| `ZSCORE_THRESHOLD` | `3.5` | 误报多调大，漏报多调小（也可交给自适应阈值自动调） |
| `SPIKE_MIN_ABS_BPS` | `104857600`（100Mbps） | 突发告警基线：低于该值一律不判突发（避免低基线噪声），达到即起报 |
| `SPIKE_BPS_THRESHOLD` | `209715200`（200Mbps） | 直达线：达到即判 `traffic_spike`（critical，自动封禁）；100~200M 内按 1.5× 基线给 high、其余给 medium |
| `BLOCK_TTL_SEC` | `1800` | 攻击频发可延长（3600+），误报困扰可缩短（600） |
| `WHITELIST_CIDRS` | 回环等 | **上线必修**：加入网关、堡垒机、监控、运维网段 |
| `ALERT_SCORE_THRESHOLD` | `6.0` | 告警太多调大（8~10）；高危业务想更敏感可调小（4~5） |
| `SCORING_WINDOW_SEC` | `300` | 慢速渗透想看得更久调大（600~900） |
| `DIRECT_ALERT_ENABLED` | `true` | 只想"多看少动"时改 `false`（全部走聚合投票） |
| `ADAPTIVE_THRESHOLD_ENABLED` | `true` | 阈值不希望被自动调整（合规要求固定阈值）时改 `false` |
| `SIGMA_RULES_ENABLED` / `ET_RULES_ENABLED` | `true` | 不接入开源规则集时改 `false`（回落到仅内置知识库） |
| `LLM_ENABLED` / `LLM_API_KEY` | `true` / 空 | 需要 AI 研判时填入 Key（DeepSeek 或任意 OpenAI 兼容接口）；不填即自动降级 |
| `LLM_MASK_INTERNAL_IP` | `true` | 合规要求更严时可保持 `true`（只发结构化摘要 + IP 脱敏） |
| `ALERT_CHANNELS` | `log` | 配置钉钉/企微/邮件/Syslog 后追加对应通道名 |
| `WEB_DETECT_ENABLED` | `true` | 关闭 HTTP 侧 Web 攻击检测时改 `false` |
| `WEB_DETECT_SOURCE` | `auto` | 生产建议 `log`（tail 访问日志）或 `api`（WAF 投递）；演示用 `demo` |
| `WEB_LOG_PATH` | 空 | `log`/`auto` 模式下要 tail 的 nginx·Apache 访问日志绝对路径 |
| `WEB_BRUTE_FORCE_ATTEMPTS` | `10` | 登录接口暴破判定次数（60 秒窗口内），误报多调大、漏报多调小 |
| `WEB_ATTACK_RULES_FILE` | 空 | 留空使用 `backend/data/web_attack_rules.json`（Web 攻击知识库） |
| `AUTH_ENABLED` | `true` | 生产保持 true；本地纯演示才临时 false |
| `ADMIN_INITIAL_PASSWORD` | 空 | 首启管理员密码；留空=随机密码（日志查看） |
| `SESSION_TTL_SEC` / `SESSION_IDLE_SEC` | 43200 / 1800 | 会话绝对/空闲有效期 |
| `COOKIE_SECURE` | `false` | 上 HTTPS 后改 true |
| `API_TOKEN` | 空 | 机器调用令牌；WAF/代理/Web 业务 高保真接入必须非空 |
| `THREAT_STORE_ENABLED` / `THREAT_RETENTION_DAYS` | true / 7 | 威胁事件留存开关与天数 |
| `RULESETS_ENABLED` / `RULES_TIERS` | true / core | 规则包与档位；extended/lab 未标定前不建议生产 |
| `RULES_SHADOW_MODE` | false | 误报标定：只记录不告警不封禁 |
| `MATCH_BACKEND` | auto | 优先 RE2；未安装自动回落 python |
| `PROTECTED_CIDRS` | 空 | 受保护网段，用于方向判定；不填则方向 unknown |
| `TRIAGE_ENABLED` | false | 研判执行器；先影子模式标定再开 |
