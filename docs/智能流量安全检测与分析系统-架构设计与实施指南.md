### 1.2 数据流（一次攻击从发生到被处置的完整链路）

```
① 流量到达网卡
   eBPF（生产）或 libpcap（兜底）捕获 → 统一封装为 FlowEvent(ts, src, dst, sport, dport, proto, bytes, flags, direction)
   ↓（回调，单包级：只做累加，不做任何计算）
② 滑动窗口累加（backend/app/collector/ring.py，O(1) 摊销、与 QPS 无关的内存占用）
   port_window(10s) / src_window(10s) / port_hits(10s) / syn_window / rst_window / 连接表
   ↓（每 tick，默认 500ms）
③ 构建 TrafficSnapshot：整机 bps/pps/连接数 + 端口 Top + 源特征(端口多样性/熵/SYN 比)
   ↓
④ DetectionEngine.evaluate()（backend/app/detection/engine.py）
   ├─ 规则 1 突发流量峰值      ：全局 bps 的 EWMA-Z + 稳健 P95 复核 + 硬阈值兜底
   ├─ 规则 2 非标准端口高频访问：端口级基线 Z-score + 标准端口白名单
   ├─ 规则 3 端口扫描          ：单源目的端口多样性 ≥ 阈值 且 端口熵 ≥ 3.0
   ├─ 规则 4 认证端口暴破      ：单源对 22/3389/3306… 的访问次数 ≥ 阈值
      └─ 规则 5 Isolation Forest  ：8 维行为向量离群确认（无监督补充）
   ↓ 产出 Anomaly(category, severity, score, source_ip, dest_port, message, evidence, detector)
④' HTTP 侧 Web 攻击检测（backend/app/detection/web_knowledge.py，知识库驱动）
   Web 请求事件（access.log tail / Web 业务 风格仿真 / POST /web/requests 投递）→ 入队
   → 字段提取（path/query/body/header/cookie/filename）
   → 归一化（多轮 URL 解码 → HTML 实体 → SQL 注释转空格 → 空白折叠 → 转小写）
   → 规则匹配（17 大类 63 条内置 + Sigma/ET 外部规则：SQL 注入/盲注、XSS 反射与存储、命令注入、
      文件包含、文件上传、暴力破解、CSRF、不安全验证码、目录穿越、SSRF、XXE、Webshell、SSTI、
      LDAP/NoSQL、CRLF）
   → 频次阈值（暴破/CSRF/验证码按窗口内累计次数）→ 组合攻击提级 → 冷却抑制
   ↓ 产出同类 Anomaly，category = web_<大类>（与流量侧告警共用下面⑤⑥⑦全部链路）
⑤ 信号评分与聚合（backend/app/detection/scoring.py，方案第 2 层）
   每个 Anomaly → Signal（权重 = 严重度 × 置信度；含规则 ID / 直达标记 / 窗口 ID）
   ├─ 直达：weight ≥ DIRECT_ALERT_WEIGHT(6.0) 或规则被标记 direct_alert → 立即告警（不等窗口到期）
   ├─ 聚合：进入该源 IP 的 300s 滑动窗口，风险分 ≥ ALERT_SCORE_THRESHOLD(6.0) 才告警
   │        （≥2 类 ×1.2、≥3 类 ×1.5、窗口含 critical ×1.3）
   └─ 抑制：阈值未达 / 冷却期内 → 仍写入 signals 表并在前端可见（禁止静默丢弃）
   ↓ 产出 AggregatedAlert（risk_score / direct_alert / contributing_rules / signal_window_id）
⑥ 三级处置（CollectorService._handle_anomaly）
   ├─ 落库      ：alerts 表（含证据快照与评分字段，可复现、可审计）+ signals 表（原子信号）
   ├─ 自动封禁  ：Blocker.block() → 白名单校验 → 防火墙下发 → block_rules 落库 → TTL 到期自动解封
   │              （门槛只由 AUTO_BLOCK_ENABLED / AUTO_BLOCK_MIN_SEVERITY 决定，评分不参与）
   ├─ 通知      ：Notifier.dispatch() → 钉钉/企微/邮件/Syslog 多通道扇出（单通道失败不影响其他）
   ├─ 推送大屏  ：EventBus.publish("alert") → SSE → 大屏弹窗 + 播报置顶 + 封禁表新增行
   └─ AI 研判   ：AlertEnricher.submit(alert_id) → 后台线程跑降级链 → 写回 alerts.llm_analysis
                  → EventBus.publish("alert_enriched") → 前端抽屉自动刷新
⑦ 人工闭环：大屏点「解封」→ DELETE /blocks/{ip} → 防火墙撤销 + 审计日志 + 白名单可加入（防误报）；
             告警「确认/封禁」反馈回流到自适应阈值重算（backend/app/detection/adaptive_threshold.py）
```

### 1.3 关键设计取舍（为什么这样分层）

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 采集放内核还是用户态 | eBPF 优先，scapy 兜底 | eBPF 在内核完成按流聚合，用户态每 tick 只读一次哈希表；CPU 随包速率、规则数与采集后端变化，不承诺固定百分比；scapy 兼容性最好但每包一次拷贝，仅作降级 |
| 检测放同步还是异步 | 与聚合同线程、按 tick 批处理 | 检测是 O(端口数+源数)，每 500ms 一次即可；避免为每包引入线程切换开销 |
| 指标存内存还是库 | 三级：内存环形缓冲（实时）→ InfluxDB（时序）→ PostgreSQL（业务） | 大屏要毫秒级，库要强一致，时序要长周期；三者职责不重叠 |
| 大屏推送用轮询还是 SSE | SSE 推送 + 轮询兜底 | 服务器→浏览器单向流，SSE 比 WebSocket 更轻（无需协议升级、天然支持断线重连）；nginx 关缓冲即可毫秒级 |
| 自动封禁是否默认开启 | 开启但 **DRY_RUN=true** + TTL + 白名单三重保护 | 自动化响应的最大风险是误封导致业务中断，默认"只记录不生效"让用户先观察告警质量 |

## 2. 技术选型清单

### 2.1 采集层（对应需求 3.1 数据源）

| 模块 | 推荐选型 | 本项目实现 | 选型理由 | 备选 |
| --- | --- | --- | --- | --- |
| 内核态流量采集 | **eBPF + BCC**（Cilium/Tetragon 同源思路） | `collector/sources.py::EBPFSource` + `ebpf_program.c` | kprobe 挂 `tcp_sendmsg`/`tcp_cleanup_rbuf`/`udp_sendmsg`，内核哈希表按流聚合；无逐包拷贝，CPU 随新建流速率增长；无需停业务、无需重启内核模块 | 需内核 4.9+ 与内核头文件，成本高时用下者 |
| 用户态抓包 | **libpcap（scapy / gopacket）** | `ScapySource` | 兼容性最好（容器/无内核头文件也能跑），BPF 过滤在内核完成、仅拷贝命中包；支持 promisc 模式 | AF_PACKET、PF_RING |
| 网卡级吞吐统计 | `nethogs` / `iftop` / `/proc/net/dev` | 未启用（由 eBPF 覆盖） | 进程级归因方便排障，但无法提供端口/源 IP 维度，仅作人工核查 | `ss -s`、`conntrack -L` |
| 无权限环境 | **内置仿真数据源** | `DemoSource` | 在 Windows 开发机/CI/演示环境稳定复现 4 类攻击剧本，保证全链路可验证 | — |

### 2.2 检测算法（对应需求 3.2）

| 方法 | 用途 | 本项目实现 | 为什么适合本场景 |
| --- | --- | --- | --- |
| **EWMA 均值/方差基线 + Z-score** | 整机带宽峰值、包速率异常 | `detection/zscore.py::EwmaBaseline` | O(1) 内存、O(1) 时间；对趋势自适应；单核可支撑 10w+ 时序键 |
| **稳健 Z-score（median/MAD）** | 非对称分布下的复核（抑制抖动误报） | `robust_zscore()` + `RollingStats` | 攻击流量本身会污染历史窗口时，MAD 不受离群点影响 |
| **端口多样性 + 端口熵** | 端口扫描识别 | `SourceSample.port_entropy`（Shannon 熵） | 单纯"端口数多"可能是正常业务；叠加熵值可区分"扫描"与"多端口正常访问" |
| **滑动窗口频次阈值** | 认证端口暴破 | `port_hits` + `BRUTE_FORCE_ATTEMPTS` | 暴破本质是短窗口高频次，规则简单、可解释、无误报放大器 |
| **Isolation Forest（无监督）** | 8 维行为向量离群确认 | `detection/iforest.py` | 无标注可用；对"连接数不高但端口熵很高"这类多维异常敏感；sklearn 缺失时自动降级，不影响主链路 |

> 判定顺序的两个关键细节（都已在代码中实现并有单测锁定）：
> 1. **先打分再更新基线**：若先 `update` 再算 Z，突增样本会立刻把均值/方差拉大、自身 Z 被稀释到阈值以下（典型漏报）；
> 2. **异常样本以 1/10 权重入基线**：防止持续性攻击把基线"拉高"，造成后续同类攻击漏报（baseline poisoning）。
> 融合策略：`severity = f(max(Z-score 归一化分, IF 离群分))`，任一通道命中即告警。

### 2.3 存储（对应需求 4 存储约束）

| 存储 | 选型 | 用途 | 理由 |
| --- | --- | --- | --- |
| 实时指标 | **内存环形缓冲**（`deque(maxlen=N)`） | 趋势图 240 点、端口/源滑窗 | 毫秒级零延迟；内存上限与 QPS 无关，只与窗口长度有关 |
| 时序库 | **InfluxDB v2**（Line Protocol over HTTP） | 流量/端口/告警指标长周期留存 | 写多读少、按时间聚合高效；HTTP 直写**不引入客户端依赖**（`collector/sink_influx.py`） |
| 关系库 | **PostgreSQL 16**（生产）/ **SQLite**（单机默认） | 资产、告警、封禁、白名单、漏洞、处置日志 | 需要事务、唯一约束与关联查询；SQLAlchemy 2.0 让两者零代码切换 |
| 降采样 | 每 10s 落 1 条整机样本 + TOP 16 端口样本 | 历史回看、容量规划 | 避免 500ms 全量落库造成写放大（一天 17 万条 → 8640 条） |

### 2.4 响应与告警（对应需求 3.3）

| 模块 | 实现 | 关键点 |
| --- | --- | --- |
| 防火墙适配 | `response/firewall.py`：iptables / nftables / firewalld / none | **列表参数调用 subprocess（等价 shell=False）+ `ipaddress` 校验**，从根上杜绝命令注入；规则统一带 `SECOPS_BLOCK` 注释便于批量回收 |
| nftables 优化 | `nft add set … { type ipv4_addr; flags interval,timeout; }` | 利用内核 timeout 元素自动到期，省掉一个清理任务 |
| 封禁编排 | `response/blocker.py` | 白名单 → 去重（命中次数累加）→ 下发 → 落库 → 审计日志 → TTL 后台自动解封 |
| 白名单 | `response/whitelist.py` | 配置内置（回环/组播）+ 数据库动态（API 维护），热路径走内存缓存 |
| 告警通道 | `alerting/channels.py` | 钉钉/企微 markdown 机器人、通用 JSON Webhook、SMTP（SSL/STARTTLS）、Syslog（RFC5424）；通道异常全部吞掉，不拖垮检测链路 |
| 告警抑制 | `engine._apply_cooldown` + `ALERT_COOLDOWN_SEC` | 同一 (类型, 源 IP) 冷却窗口内只报一次，避免告警风暴 |
| 干跑模式 | `DRY_RUN=true`（默认） | 只预演命令、不写内核表；Windows/CI 也能验证封禁链路 |

### 2.6 前端与部署

| 模块 | 选型 | 理由 |
| --- | --- | --- |
| 图表 | **ECharts 4.0.3**（沿用模板自带库） | 大屏生态成熟，增量 `setOption` 对 500ms 刷新毫无压力；零网络依赖 |
| 前端框架 | 原生 JS（本仓库）→ **Vue 3**（可选升级，见 3.2） | 本仓库以"零构建、可直接双击打开"为目标；同时给出 Vue3 等价实现便于接入既有工程 |
| 实时通道 | **SSE**（`EventSource`） | 单向推送足够、断线自动重连；nginx 侧仅需 `proxy_buffering off` |
| 后端框架 | **FastAPI + Uvicorn** | 原生 async、Pydantic 契约、自动 OpenAPI 文档，最契合"REST + SSE"混合形态 |
| 并发模型 | 采集/检测/解封/Influx 各 1 个后台线程，API 走线程池 | 抓包库是阻塞式的，线程模型比强行 async 更稳 |
| 部署 | **Docker Compose**（PostgreSQL + InfluxDB + 后端 + nginx）+ 裸机 `install.sh` | 一键起；host 网络覆盖文件解决"真抓包 + 真封禁"的内核能力需求 |
| 免 root 抓包 | `setcap cap_net_raw,cap_net_admin+eip <python>` | 比长期以 root 运行更安全；systemd 侧同时提供 `AmbientCapabilities` |

### 2.7 智能增强层（v2：规则 / 评分 / 自适应 / 研判）

| 模块 | 实现 | 关键点 |
| --- | --- | --- |
| 统一规则层 | `rules/base.py`（Schema）、`native_loader` / `sigma_loader` / `et_loader` / `cve_ext_loader`（来源）、`registry.py`（索引 + 热加载） | 四种来源归一化为同一 `Rule`；`direct_alert` 按类别白名单 + `critical×high` 自动注入；类别无法映射的规则**加载期跳过**（宁可少加载，不可错加载）；加载失败只降级该来源，不抛异常 |
| 滑动窗口评分 | `detection/scoring.py::ScoringAggregator` | 每个 signal 到达即评估（**不等窗口到期**，告警延迟 ≈ 1 个 tick）；权重 = 严重度 × 置信度；多类别/critical 加成；per-source 冷却复用 `ALERT_COOLDOWN_SEC`；窗口上限保护 |
| 直达机制 | 同上（`direct_alert` / `DIRECT_ALERT_WEIGHT=6.0`） | critical+high 恰好 6.0 = 直达阈值；直达是**规则固有属性**，不参与自适应阈值调整（避免削弱对致命攻击的响应） |
| 自适应阈值 | `detection/adaptive_threshold.py` | 维度 = `检测类型 × 资产口径 × 时段`；`/alerts` 人工反馈判定真阳（封禁）/误报（确认关闭）；FP 率驱动收放，幅度夹在静态基准 0.5~2.0 倍并设最小样本；人工覆盖的记录自动跳过 |
| AI 研判降级链 | `analysis/fallback_chain.py`（编排）、`llm_client.py`（OpenAI 兼容）、`template_responder.py`（模板）、`enricher.py`（异步队列 + 工作线程） | 采集线程没有事件循环，故用**守护线程 + 定长队列**实现"提交即返回"；Prompt 只含结构化摘要 + IP 脱敏（防注入）；输出过 schema 校验，非法即降级；每级都写 `source`/`degraded` |
| 可观测性 | `GET /rules/sources`、`/scoring/config`、`/signals`、`/thresholds` + 启动日志 | 启动日志 `rules loaded: native=…, sigma=…, et=…, cve_ext=…, direct_alert=…`；被抑制的 signal 可查，降级来源可查 —— **禁止静默降级** |

### 3.1 捕获特定端口异常流量并触发 iptables 封禁（Python）

完整实现在 `backend/app/detection/engine.py` + `backend/app/response/blocker.py` + `backend/app/response/firewall.py`。
下面给出**可直接复用的最小闭环**（剥离框架依赖，仅保留关键逻辑）：

```python
"""最小可用示例：非标准端口高频访问 → 自动 iptables 封禁（含白名单与 TTL）。

对应仓库实现：
  backend/app/detection/engine.py::DetectionEngine._detect_ports   —— 规则判定
  backend/app/response/blocker.py::Blocker.block                   —— 封禁编排
  backend/app/response/firewall.py::IptablesBackend                —— 命令下发
"""
from __future__ import annotations

import ipaddress
import logging
import shutil
import subprocess
import time
from collections import defaultdict, deque

logger = logging.getLogger(__name__)

STANDARD_PORTS = {20, 21, 22, 23, 25, 53, 80, 110, 143, 443, 465, 993, 995,
                  1433, 1521, 3306, 3389, 5432, 5900, 6379, 8000, 8080, 8443, 9200, 27017}
WHITELIST = [ipaddress.ip_network(cidr, strict=False) for cidr in
             ("127.0.0.1/32", "169.254.0.0/16", "192.168.0.0/16")]   # 生产按需收紧
WINDOW_SEC, PPS_THRESHOLD, TTL_SEC = 10.0, 300.0, 1800
DRY_RUN = True          # ★ 默认干跑：只记录不生效，验证无误后再改 False
PORT_BASELINE: dict = {}


# --------------------------------------------------------------------------- #
# 1) 滑窗聚合：单包只做累加，检测放到窗口边界执行（避免每包计算）
# --------------------------------------------------------------------------- #
class PortWindow:
    def __init__(self, window_sec: float) -> None:
        self.window = window_sec
        self._hits: dict = defaultdict(deque)          # (src_ip, dport) -> [(ts, pkts)]

    def add(self, src_ip: str, dst_port: int, pkts: int = 1, ts: float | None = None) -> None:
        self._hits[(src_ip, dst_port)].append((ts or time.time(), pkts))

    def rates(self, now: float | None = None) -> dict:
        """返回 {(src_ip, dport): pps}，同时淘汰窗口外数据。"""
        now = now or time.time()
        cutoff, result = now - self.window, {}
        for key, bucket in list(self._hits.items()):
            while bucket and bucket[0][0] < cutoff:
                bucket.popleft()
            if not bucket:
                del self._hits[key]
                continue
            result[key] = sum(pkts for _ts, pkts in bucket) / self.window
        return result


# --------------------------------------------------------------------------- #
# 2) 判定 + 封禁：白名单闸门 → 参数化命令 → 自助回滚
# --------------------------------------------------------------------------- #
def validate_target(ip: str) -> str:
    """命令行安全边界：只允许合法 IP/CIDR，杜绝注入（如 `1.2.3.4; rm -rf /`）。"""
    ip = ip.strip()
    ipaddress.ip_network(ip, strict=False) if "/" in ip else ipaddress.ip_address(ip)
    return ip


def is_whitelisted(ip: str) -> bool:
    try:
        addr = ipaddress.ip_address(ip)
    except ValueError:
        return True                       # 非法输入一律不放行封禁
    return any(addr in net for net in WHITELIST)


def block_ip(ip: str, reason: str, ttl_sec: int = TTL_SEC) -> tuple:
    ip = validate_target(ip)
    if is_whitelisted(ip):
        logger.info("命中白名单，拒绝封禁: %s", ip)
        return False, "whitelisted"

    # 关键点 1：参数以 list 传入（等价 shell=False）→ 无 shell 解析、无注入
    # 关键点 2：-m comment 打标记，便于精确回滚与批量审计
    cmd = ["iptables", "-I", "INPUT", "1", "-s", ip,
           "-m", "comment", "--comment", "SECOPS_BLOCK", "-j", "DROP"]

    if DRY_RUN:
        logger.warning("[DRY-RUN] %s（原因：%s，TTL=%ss）", " ".join(cmd), reason, ttl_sec)
        return True, "dry-run"

    if shutil.which("iptables") is None:
        return False, "iptables 未安装"
    proc = subprocess.run(cmd, capture_output=True, text=True, timeout=15, check=False)
    if proc.returncode != 0:
        return False, (proc.stderr or proc.stdout).strip()
    schedule_auto_unblock(ip, ttl_sec)    # TTL 到期自动解封，防"一次误判永久断网"
    return True, " ".join(cmd)


def schedule_auto_unblock(ip: str, ttl_sec: int) -> None:
    """生产实现见 Blocker.start_reaper()：后台线程每 10s 扫描到期规则并解封。"""
    logger.info("已登记自动解封任务: %s 将于 %ss 后解封", ip, ttl_sec)


# --------------------------------------------------------------------------- #
# 3) 主循环骨架（真实实现由 CollectorService._tick 驱动，默认 500ms 一次）
# --------------------------------------------------------------------------- #
def watch_loop(packet_iterator, dry_run: bool = True) -> None:
    """packet_iterator 产出 (src_ip, dst_port, pkts)；生产环境用 eBPF/libpcap 替换。"""
    global DRY_RUN
    DRY_RUN = dry_run
    window, last_tick = PortWindow(WINDOW_SEC), time.time()

    for src_ip, dst_port, pkts in packet_iterator:
        window.add(src_ip, dst_port, pkts)

        if time.time() - last_tick < 0.5:          # 每 500ms 做一次检测
            continue
        last_tick = time.time()

        for (src, port), pps in window.rates().items():
            if port in STANDARD_PORTS:             # 标准端口流量大属正常，跳过
                continue
            if pps < PPS_THRESHOLD:
                continue
            # 基线复核：同一端口长期高流量是业务特征，需靠基线区分"突发"与"常态"
            # 生产版此处使用 EWMA-Z（DetectionEngine.port_pps）并叠加 P95 复核
            baseline = PORT_BASELINE.get((src, port), 0.0)
            if baseline and pps < baseline * 3:
                PORT_BASELINE[(src, port)] = 0.3 * baseline + 0.7 * pps
                continue

            ok, detail = block_ip(src, f"非标准端口 {port} 高频访问 {pps:.0f} pps", TTL_SEC)
            logger.warning("封禁结果 %s: %s -> %s", ok, src, detail)
            PORT_BASELINE[(src, port)] = max(baseline, pps * 0.5)
```

**三个安全要点**（也是评审最常追问的点）：

1. **不使用 `shell=True` + 字符串拼接**：`subprocess.run(list)` 不经 shell 解析，配合 `ipaddress` 校验，注入面收敛为 0；
2. **白名单前置**：封禁前先过 CIDR 白名单，回环/组播/办公网出口永不封禁；
3. **TTL + DRY_RUN 双保险**：任何自动封禁都有 30 分钟生命周期（到期自动解封），且默认只记录不生效。

```bash

# 精确回滚（生产通过 API：DELETE /api/v1/blocks/{ip}）
iptables -D INPUT -s 203.0.113.66 -m comment --comment SECOPS_BLOCK -j DROP
```

### 3.2 前端实时折线图的数据绑定（Vue 3 + ECharts）

本仓库大屏采用**原生 JS** 实现（零构建、可直接双击打开），核心逻辑在
`dashboard/js/dashboard.js::renderMetrics`：SSE 每收到一帧就向环形缓冲追加一个点，
再 `setOption` 增量更新（不重建实例、不整表刷新）。

同一思路的 **Vue 3 Composition API** 版本（便于接入既有前端工程）：

```vue
<!-- TrafficTrend.vue —— 带宽利用率 / 包速率 双 Y 轴实时折线 -->
<template>
  <div class="panel">
    <div class="title"><span>实时流量趋势（500ms 刷新）</span></div>
    <div ref="chartRef" class="chart"></div>
  </div>
</template>

<script setup>
import { onBeforeUnmount, onMounted, ref, shallowRef } from 'vue'
import * as echarts from 'echarts'

const chartRef = ref(null)
const chart = shallowRef(null)      // ECharts 实例无需响应式代理
const MAX_POINTS = 240              // 与后端 TREND_POINTS 对应
let source = null
let onResize = null

/** 环形缓冲：push + shift，内存恒定 */
const buffer = { bpsIn: [], bpsOut: [], pps: [] }

function pushPoint(target, point) {
  target.push(point)
  if (target.length > MAX_POINTS) target.shift()
}

function buildOption() {
  return {
    tooltip: { trigger: 'axis' },
    legend: { data: ['入站带宽', '出站带宽', '包速率'], textStyle: { color: '#9fd8ff' } },
    grid: { left: '7%', right: '8%', top: '20%', bottom: '13%' },
    xAxis: { type: 'time', axisLabel: { color: '#9fd8ff' } },
    yAxis: [
      { type: 'value', name: '带宽', axisLabel: { formatter: v => `${(v / 1e6).toFixed(1)}M` } },
      { type: 'value', name: '包速率', splitLine: { show: false } }
    ],
    series: [
      { name: '入站带宽', type: 'line', smooth: true, showSymbol: false, yAxisIndex: 0,
        lineStyle: { color: '#00ffff', width: 2 },
        areaStyle: { color: 'rgba(0,255,255,0.25)' }, data: [] },
      { name: '出站带宽', type: 'line', smooth: true, showSymbol: false, yAxisIndex: 0,
        lineStyle: { color: '#7bdd43', width: 2 },
        areaStyle: { color: 'rgba(123,221,67,0.2)' }, data: [] },
      { name: '包速率', type: 'line', smooth: true, showSymbol: false, yAxisIndex: 1,
        lineStyle: { color: '#febe12', type: 'dashed' }, data: [] }
    ]
  }
}

/** 每帧只更新 series.data：ECharts 内部增量 diff，数百点规模下是毫秒级 */
function applyFrame(frame) {
  const ts = (frame.ts ?? Date.now() / 1000) * 1000
  pushPoint(buffer.bpsIn, [ts, frame.bps_in ?? 0])
  pushPoint(buffer.bpsOut, [ts, frame.bps_out ?? 0])
  pushPoint(buffer.pps, [ts, (frame.pps_in ?? 0) + (frame.pps_out ?? 0)])
  chart.value?.setOption({
    series: [{ data: buffer.bpsIn }, { data: buffer.bpsOut }, { data: buffer.pps }]
  }, { lazyUpdate: true })          // lazyUpdate：合并到下一帧渲染，避免高频抖动
}

/** 首屏用 REST 补 120s 历史，避免刷新后曲线从 0 开始 */
async function bootstrap(baseUrl = '/api/v1') {
  const trend = await fetch(`${baseUrl}/metrics/trend?window_sec=120`).then(r => r.json())
  trend.bps_in.forEach(([ts, v]) => pushPoint(buffer.bpsIn, [ts * 1000, v]))
  trend.bps_out.forEach(([ts, v]) => pushPoint(buffer.bpsOut, [ts * 1000, v]))
  trend.pps_in.forEach(([ts, v], i) => {
    pushPoint(buffer.pps, [ts * 1000, v + (trend.pps_out[i]?.[1] ?? 0)])
  })
  chart.value?.setOption({
    series: [{ data: buffer.bpsIn }, { data: buffer.bpsOut }, { data: buffer.pps }]
  })
}

function connect(baseUrl = '/api/v1') {
  source = new EventSource(`${baseUrl}/stream/metrics`)
  source.addEventListener('metrics', event => applyFrame(JSON.parse(event.data)))
  source.onerror = () => console.warn('实时流中断，浏览器将自动重连…')
}

onMounted(async () => {
  chart.value = echarts.init(chartRef.value)
  chart.value.setOption(buildOption())
  await bootstrap()
  connect()

  onResize = () => chart.value?.resize()
  window.addEventListener('resize', onResize)
})

onBeforeUnmount(() => {
  window.removeEventListener('resize', onResize)
  source?.close()
  chart.value?.dispose()            // 卸载时释放实例，防内存泄漏
})
</script>
```

**绑定逻辑的三个关键点**：

1. **首屏 + 增量结合**：先用 `GET /metrics/trend` 拉 120s 历史填充曲线，再用 SSE 增量追加，
   解决"刷新页面后曲线从零开始"的观感问题；
2. **环形缓冲 + `lazyUpdate`**：`push + shift` 保证内存恒定；`lazyUpdate: true` 让 ECharts 合并渲染，
   500ms/帧（甚至 100ms/帧）也不掉帧；
3. **`shallowRef` 持有实例**：ECharts 实例不需要响应式深度代理；卸载时 `close()` + `dispose()`。

## 5. 潜在风险、性能瓶颈与优化建议

### 5.1 性能瓶颈与优化

| 瓶颈 | 现象 | 根因 | 优化思路 |
| --- | --- | --- | --- |
| 用户态抓包在大流量下丢包 | `scapy` 模式 >1Gbps 时丢包率上升、bps 偏低 | 每包一次内核→用户态拷贝 + Python 解析 | ① 切 `CAPTURE_MODE=ebpf`；② 用 BPF 过滤只抓关注流量（默认已排除 ARP/IPv6）；③ 极端场景用 AF_PACKET + PACKET_MMAP 或 XDP |
| 检测线程与抓包线程抢 GIL | CPU 升高、tick 抖动 | Python 单解释器限制 | ① 降低 `TICK_INTERVAL_MS` 频率（500→1000ms）；② 只对 TOP N 端口/源做基线判定（当前 64 个）；③ 高负载场景把检测下沉到 eBPF map（内核侧聚合） |
| 关系库写放大 | SQLite/PG 磁盘 IO 高 | 每 tick 落库 | 已做降采样（10s 一条 + TOP16 端口）；还可调大 `TICK_INTERVAL_MS` 或改批量提交 |
| 大屏高频刷新 | 浏览器 CPU 高、掉帧 | 500ms × 多个图表 | ① 图表 `setOption(..., {lazyUpdate: true})`；② 非关键面板降到 2s；③ 页面不可见时暂停（`document.hidden`） |
| 连接表膨胀 | 内存缓慢上涨 | 大量短连接残留 | 已有 `CONN_IDLE_TIMEOUT_SEC`（默认 120s）空闲回收；如长期仍上涨，可再加连接表条数上限 + LRU 淘汰（当前版本未实现） |
| 扫描任务阻塞 | API 超时 | nmap 串行扫描大网段 | ① `SCAN_TARGETS` 限制 ≤256 地址（已内置上限）；② 扫描放独立线程/队列，接口只返回任务 ID |
| 内存中的趋势缓冲 | 长时间运行内存占用 | 每个图表 600 点 × 多条序列 | `TREND_POINTS` 可调；默认配置下常驻内存为百 MB 级，规则包 696 条约 5.3 MB，RE2 索引受 `RE2_MAX_MEM_MB` 约束 |

### 5.2 安全盲区与风险

| 风险 | 说明 | 缓解措施 |
| --- | --- | --- |
| **加密流量不可见** | TLS/QUIC 之后的内容无法检测（只能看元数据） | 元数据检测仍然有效（端口/包速率/连接时长/熵）；如需内容级检测，接入 TLS 指纹（JA3/JA4）或旁路解密 |
| **内网横向移动识别有限** | 只按源 IP 聚合，缺少用户/资产身份维度 | 关联 DHCP/DNS 日志做 IP→主机名映射；对关键资产单独设更严格阈值 |
| **误封导致业务中断** | 自动响应的最大风险 | `DRY_RUN` 默认开、`BLOCK_TTL_SEC` 自动解封、`WHITELIST_CIDRS` 白名单、`AUTO_BLOCK_MIN_SEVERITY` 只封高危、封禁前后大屏可一键解封 |
| **检测阈值水土不服** | 不同业务流量差异大，默认阈值可能误报/漏报 | 首周只开 DRY_RUN 观察；用 `/alerts/stats` 复盘；再用 `ZSCORE_THRESHOLD`、`SPIKE_BPS_THRESHOLD`、`PORT_SCAN_UNIQUE_PORTS` 逐项标定 |
| **告警疲劳** | 攻击持续时告警刷屏 | `ALERT_COOLDOWN_SEC` 抑制同类重复告警；邮件通道仅 >= high；Webhook 有超时与失败隔离 |
| **接口未鉴权** | 内网免认证便于上手，但暴露风险 | 生产设置 `API_TOKEN`；nginx 层再加 IP 白名单/Basic Auth；不要把 8000/8080 直接暴露到公网 |
| **命令注入** | 封禁 IP 来自流量，属不可信输入 | 参数化 subprocess + `ipaddress` 校验 + 单元测试（含 `; rm -rf /` 用例） |
| **容器能力过大** | `NET_ADMIN` 可改宿主机网络（host 模式） | 仅在需要真封禁时使用 host 覆盖文件；默认 bridge + DRY_RUN |
| **数据留存合规** | 抓到的元数据可能含敏感信息 | 只存聚合指标与告警证据（不含 payload）；按需设置 PostgreSQL/InfluxDB 保留策略 |
| **单点故障** | 单进程采集，进程崩溃即断监控 | systemd `Restart=always` / compose `restart: unless-stopped`；告警通道可加保活心跳 |

### 5.3 进一步演进建议

1. **检测下沉**：把"端口多样性/包速率阈值"等规则做成 XDP 程序，实现线速阻断（当前方案是"检测在用户态、阻断在内核"）；
2. **行为画像**：以资产为单位维护 24h 行为向量，用轻量 LSTM/AutoEncoder 替代单点 Z-score，降低对阈值的依赖；
3. **情报联动**：接入威胁情报（IP 信誉库/GeoIP），把来源地、ASN、信誉分纳入 severity 计算；
4. **SOAR 编排**：把封禁动作抽象为可编排剧本（先取证→再封禁→再通知→再复盘），支持人工审批节点；
5. **高可用**：采集侧多副本 + 主备选举（避免重复封禁），存储侧 PostgreSQL 流复制 + InfluxDB 集群；
6. **规则生态**：把 Sigma / ET 规则同步做成定时拉取任务（当前是"放文件 + 热加载"），并接入更多来源
   （nuclei-templates、YARA-L），统一在 `/rules/sources` 里呈现；
7. **研判质量闭环**：把 `llm_analysis.verdict` 与人工处置结果（确认/误报）做成混淆矩阵看板，
   用真实反馈校准模板与 prompt（本期只做了"来源可见 + 可重研判"）。

> v2 已落地的部分（不再列为演进项）：规则库统一加载与热加载、滑动窗口评分与直达机制、
> 维度化自适应阈值、AI 研判四级降级链。

### C.2 防误报设计（关键取舍）

1. Web 业务 规则只在明确漏洞路径 + 真实攻击载荷下命中；正常 `?id=1`、`?name=guest` 不告警；
2. Web 告警自动封禁必须由直达规则确认（`WEB_AUTO_BLOCK_REQUIRES_DIRECT=true`）；
3. `WEB_IGNORE_IPS`（Web 检测）与 `DETECT_IGNORE_IPS`（流量统计）分别抑制自访问/自扫描；
4. CVE 规则在版本未知时默认不命中（`assume_risk_if_unknown` 默认 `false`）；
5. Web 漏扫每条结论都要求 HTTP 200 + 页面标记，未认证时不猜测模块漏洞；
6. AI 只生成建议/研判，不参与"是否封禁"的判定；API 不可用时逐级降级且前端标注来源。

### C.3 处理链路（攻击 → 封禁）

```
Apache access.log (8080) ──tail──► WebAttackDetector
   ├─ Web 业务 严格规则命中（direct_alert=true）
   ├─ 评分聚合（直达绕过窗口投票）
   ├─ 落库 alerts + signals（被抑制也可见）
   ├─ Blocker：白名单 → iptables/nftables/firewalld → TTL 自动解封
   ├─ Notifier：钉钉/企微/Webhook/邮件/Syslog
   └─ SSE：alert / signal / alert_enriched → 大屏
```

* **过程中真实修复的缺陷**（均为自动化测试发现，非纸面推演）：
  1. **Z-score 漏报**：原实现"先更新基线再打分"，突增样本会稀释自身 Z 值 → 改为"先打分后更新"，
     并让异常样本仅以 1/10 权重进入基线（防 baseline poisoning）；
  2. **CVE 版本区间比较错误**：`version_between` 原实现比较逻辑颠倒，导致版本高于修复版本仍被判风险；
  3. **DRY-RUN 与命令存在性耦合**：原实现要求二进制存在才能预演 → 改为干跑模式不依赖二进制，
     因此可在 Windows/CI 上安全验证封禁链路；
  4. **封禁结果语义不清晰**：新增 `code`（ok/whitelisted/duplicated/firewall_failed），
     便于大屏与第三方系统分支处理；
  5. **v2 期间修复的缺陷**：① Sigma 规则文件用 `---` 分隔多文档时只读到了第一条（改用 `safe_load_all`）；
     ② 新增列在旧库上缺失导致 `no such column`（补 `scripts/migrate_v2.py`，并为 JSON 列补 `DEFAULT '[]'`）；
     ③ `snippet` 等攻击者可控字段原本会进入 LLM Prompt（改为白名单证据摘要 + IP 脱敏）；
     ④ 规则正则的"多字段 AND / 字段内 OR"语义在扁平结构下容易误报（用 `match_all` 还原 Sigma 语义，
     并在测试里用正常流量样本回归）。

> 在 Windows 开发机上无法端到端验证；代码路径已按"单通道失败不影响主流程"实现，

## 附录 A：参数调优速查（`.env`）

| 参数 | 默认 | 调大 / 调小的效果 |
| --- | --- | --- |
| `TICK_INTERVAL_MS` | 500 | 调小 → 大屏更灵敏、CPU 略升；调大 → 更省资源 |
| `ZSCORE_THRESHOLD` | 3.5 | 调大 → 更保守（少误报、可能漏报）；调小反之 |
| `SPIKE_MIN_ABS_BPS` | 100Mbps | 突发告警基线：低于该值不判突发；达到即起报（相对基线 1.5 倍以上给 high，其余给 medium） |
| `SPIKE_BPS_THRESHOLD` | 200Mbps | 硬阈值/直达线：达到即 critical 并触发自动封禁；按业务峰值带宽的 1.5~2 倍设置 |
| `PORT_SCAN_UNIQUE_PORTS` | 60 | 内网资产多时可调大，避免正常巡检误报 |
| `BRUTE_FORCE_ATTEMPTS` | 40 | 内网有自动化运维工具时调大，或把运维 IP 加白名单 |
| `CONN_IDLE_TIMEOUT_SEC` | 120 | 有长轮询/消息推送业务时调大（如 900），避免活跃连接被误回收 |
| `AUTO_BLOCK_MIN_SEVERITY` | high | 保守运维可设为 `critical`，只封最确定的攻击 |
| `BLOCK_TTL_SEC` | 1800 | 调小更适合快速放行误封，调大减少重复封禁频率 |
| `ALERT_COOLDOWN_SEC` | 60 | 攻击持续时调大以抑制刷屏（评分冷却期同样复用该值） |
| `WHITELIST_CIDRS` | 回环/组播 | **务必加入**网关、堡垒机、监控节点、运维办公网段 |
| `ALERT_SCORE_THRESHOLD` | 6.0 | 调大 → 聚合告警更少（更多信号被抑制）；调小 → 更容易告警 |
| `SCORING_WINDOW_SEC` | 300 | 调大 → 慢速渗透更容易被累计到阈值；调小 → 只看瞬时爆发 |
| `DIRECT_ALERT_ENABLED` | true | 设为 `false` → 所有告警都走聚合投票（适合"先观察再响应"阶段） |
| `DIRECT_ALERT_WEIGHT` | 6.0 | 调低 → 更多高置信度规则变成"一命中就告警"；调高相反 |
| `ADAPTIVE_THRESHOLD_ENABLED` | true | 设为 `false` → 阈值固定为配置值（不随误报反馈漂移） |
| `THRESHOLD_RECOMPUTE_INTERVAL_SEC` | 21600 | 误报反馈变化快（新业务上线）时可调到 3600 |
| `THRESHOLD_FP_HIGH` / `FP_LOW` | 0.5 / 0.1 | 收紧/放松的触发线；想更保守就把 `FP_HIGH` 调低 |
| `LLM_ENABLED` / `LLM_API_KEY` | true / 空 | 填 Key 才启用模型研判；不填或接口故障自动降级，不影响告警 |
| `LLM_TIMEOUT_SEC` | 3.0 | **必须远小于告警节奏**；网络慢也不要超过 5s（研判是异步的，但过大会积压队列） |
| `LLM_MASK_INTERNAL_IP` | true | 合规要求"外发数据最小化"时保持 `true`（只发结构化摘要 + IP 脱敏） |

## 附录 B：常见故障排查

| 现象 | 排查 | 处理 |
| --- | --- | --- |
| 大屏显示「演示数据」 | `curl /api/v1/health` 是否可达 | 后端未启动或跨域；确认 `DASHBOARD_DIR` 与 API 地址（可用 `?api=http://ip:8000/api/v1` 覆盖） |
| `capture_mode=demo` 且非预期 | 看启动日志中"降级"提示 | 无权限 → 用 root 或 `setcap`；无 scapy → 装依赖；容器 → 加 `NET_RAW` 与 host 网络 |
| 告警一直不出现 | `GET /api/v1/status` 看 `ticks` 是否增长 | 确认流量确实命中阈值；调小 `ZSCORE_THRESHOLD` / `SPIKE_BPS_THRESHOLD`；检查 `ALERT_COOLDOWN_SEC` |
| 封禁返回成功但 `iptables -L` 无规则 | `DRY_RUN` 是否为 true | 置 `DRY_RUN=false`；确认后端是 `iptables` 而非 `none` |
| 大屏趋势图不动 | `curl -N /api/v1/stream/metrics` | nginx 需 `proxy_buffering off`；浏览器需支持 EventSource（IE 不支持） |
| 服务重启后封禁丢失 | 检查 `/blocks?active_only=true` | 规则在数据库；重启后如需恢复内核规则，可在启动钩子中重放未过期记录（当前默认不重放，避免误伤） |
