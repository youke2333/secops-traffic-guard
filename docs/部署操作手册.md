# 智能流量安全检测与分析系统 · 部署操作手册

> **适用对象**：具备基础计算机操作能力（会登录 Linux、会改配置文件、会看日志）的安防运维人员，不要求会写代码。
> **适用系统**：Ubuntu Server 22.04 / 24.04 LTS（CentOS、麒麟的差异见 1.2）。
> **手册版本**：v6，对应《系统更新方案-v6》。
> **约定**：所有命令以 `$` 表示普通用户、`#` 表示 root；带 ⚠ 的步骤有封禁或断网风险，务必先读完再执行。

## 0. 开始之前

### 0.1 这套系统能做什么

| 能力 | 说明 | 你需要准备 |
|---|---|---|
| 流量监控 | 带宽、包速率、会话、端口 TOP | 一块能抓到业务流量的网卡 |
| 威胁告警 | 记录疑似攻击流量的请求/响应、规则、方向、标签 | 目标机访问日志，或代理，或镜像口 |
| 封禁管理 | 自动/手动封禁、TTL 自动解封、白名单 | 防火墙权限 |
| 安全事件报告 | 按 IP 汇总证据，生成可打印 HTML | 无 |
| 规则运营 | 规则包分档、影子模式、匹配后端切换；自定义规则上传/回滚为后续批次 | 无 |
| 登录与审计 | 三角色、会话、操作审计 | 无 |

### 0.2 手册与版本的对应关系

本手册描述的是**完成 v6 可用部分**的系统。各能力的实际上线状态如下（未上线的功能不要按“已支持”操作）：

| 功能 | 本版本状态 | 说明 / 替代方案 |
|---|---|---|
| 登录页、用户管理、审计 | ✅ 已上线 | 默认 `AUTH_ENABLED=true`；首次密码见 3.7 |
| 威胁告警页、封禁管理页 | ✅ 已上线 | `threat.html` / `block.html`；`response.html` 自动跳转 |
| 威胁详情、九章报告、CSV 导出 | ✅ 已上线 | 威胁页详情、封禁页“生成报告” |
| 规则包分档、RulePlan / RE2 | ✅ 已上线（HTTP 规则） | 规则管理页可切换档位与后端 |
| 研判执行器 | ✅ 已实现，默认关闭 | `TRIAGE_ENABLED=false`；先影子模式标定 |
| 流级规则执行器 / 病毒文件扫描（P3） | ⏳ 后续批次 | 保持 `FLOW_RULES_ENABLED=false`、`MALWARE_SCAN_ENABLED=false` |
| 防火墙/镜像采集后端（P4） | ⏳ 后续批次 | 继续用日志或代理；**不要**设 `CAPTURE_MODE=firewall` |
| 自定义规则上传页面（P5） | ⏳ 后续批次 | 本版本只读展示规则包，不提供上传入口 |

> 判断方法：打开 `http://<服务器IP>:8000/`，左侧导航有“威胁告警”“封禁管理”“规则管理”即为新版本；没有则是旧版本。

### 0.3 先选部署形态

```
你的服务器能拿到什么？
├── 只拿得到 Apache/Nginx 访问日志 ──────────→ 形态 1：日志模式（最简单，先做这个）
├── 能装代理，且接受改业务端口 ─────────────→ 形态 2：代理模式（能看到完整请求体）
├── 服务器就是网关/防火墙，或能接镜像口 ────→ 形态 3：防火墙/镜像（⏳ 后续批次，当前不可用）
└── 什么都没有，只想演示 ──────────────────→ 形态 0：仿真模式（DemoSource）
```

| 形态 | 能看到 | 看不到 | 资源开销 | 适用 |
|---|---|---|---|---|
| 0 仿真 | 内置攻击剧本 | 真实流量 | 最低 | 演示、培训 |
| 1 日志 | URL、查询串、UA、状态码 | POST body、响应体 | 低 | 已有 Web 服务 |
| 2 代理 | 完整请求 + 可选响应 | 非 HTTP 流量 | 中 | 需要取证 |
| 3 防火墙/镜像 | 五元组、包长、flags、方向 | HTTP 内容 | 中低 | 网关、旁路（当前未实现） |

**建议**：第一次部署一律从形态 1 开始，跑通“检测 → 告警 → 报告”；需要请求体再上形态 2。

### 0.4 部署前信息收集表（先填好再动手）

| 项目 | 你的值 | 怎么查 |
|---|---|---|
| 服务器 IP | | `hostname -I` |
| 管理网段 | | 你的办公电脑 IP 段 |
| 采集网卡名 | | `ip -br a`（VMware NAT 常见 `ens33`） |
| 业务 Web 端口 | | 如 8080 |
| 访问日志路径 | | `ls /var/log/apache2/` |
| 日志格式 | | `tail -1 <日志>` 看是否有 `host:port` 前缀 |
| 受保护网段 | | 如 `192.168.152.0/24` |
| 是否允许改防火墙 | 是/否 | 问业务负责人 |
| 封禁时长 | 建议 600–1800 秒 | 与业务约定 |

### 0.5 时间与风险

- 首次部署约 **60–90 分钟**（不含被测业务站点）。
- 安装过程会重启后端服务，**不影响被监控业务**（旁路/日志模式）。
- ⚠ 只有把 `DRY_RUN` 改成 `false` 才会真正修改防火墙；在此之前所有封禁都只是记录。

## 1. 部署前检查

### 1.1 硬件与系统

| 项目 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| CPU | 2 核 | 4 核 | 规则全开 + 抓包时 CPU 是瓶颈 |
| 内存 | 4 GB | 8 GB | 规则对象、队列、数据库缓存 |
| 磁盘 | 40 GB | 100 GB | 威胁事件默认留 7 天，约 0.4–0.7 GB |
| 系统 | Ubuntu 22.04 LTS | Ubuntu 22.04 / 24.04 LTS | 需要 `python3` ≥ 3.10 |
| 架构 | x86_64 | x86_64 | ARM 需自行确认 RE2 wheel |

检查命令：

```bash
lsb_release -a          # 看版本
nproc                   # 核数
free -h                 # 内存
df -h /opt              # 磁盘
python3 --version       # 需 3.10 及以上
```

### 1.2 其他发行版的差异

| 系统 | 包管理 | 注意 |
|---|---|---|
| CentOS 7 / 麒麟 V10 | `yum` | Python 可能 3.6，需先装 3.10；`firewalld` 默认开启 |
| openEuler | `dnf` | 同上 |
| Debian 12 | `apt` | 与 Ubuntu 基本一致 |

如果 `python3 --version` 低于 3.10，先装新版 Python，再执行 `deploy/install.sh`（脚本会用 `PY_BIN` 指定的解释器）：

```bash
sudo apt install -y python3.10 python3.10-venv
sudo PY_BIN=python3.10 bash deploy/install.sh --web-profile
```

### 1.3 网络要求

| 用途 | 要求 |
|---|---|
| 管理访问 | 你的电脑能访问服务器 8000（或 80/443） |
| 日志采集 | 服务器能读目标机日志（同机最简单；跨机用 rsync/syslog 汇总） |
| 镜像/网关采集 | 采集网卡能看到业务流量；VMware 需在虚拟网络编辑器里把网卡设为混杂模式 |
| 出站 | 可选：AI 研判需要访问 `api.deepseek.com`；离线部署可关闭 |

### 1.4 端口清单

| 端口 | 用途 | 谁访问 | 是否可改 |
|---|---|---|---|
| 8000 | 后端 + 大屏（默认） | 管理员 | `install.sh` 内固定，改需改 systemd |
| 80/443 | nginx 反代（可选） | 管理员 | 是 |
| 8080 | 被测业务站点（仅演练） | 攻击机 | 是 |
| 8081 | 业务站点真实端口（代理模式） | 本机代理 | 是 |

### 1.5 权限要求

| 能力 | 用途 | 授予方式 |
|---|---|---|
| `sudo` | 安装、改配置、重启服务 | 安装时创建的用户 |
| `adm` 组 | 读 `/var/log/apache2/*` | `sudo usermod -aG adm <用户>` |
| `CAP_NET_RAW` | 抓包 | `install.sh` 自动 `setcap` 或 systemd `AmbientCapabilities` |
| `CAP_NET_ADMIN` | 改 iptables | 同上 |

### 1.6 开机前检查表

- [ ] 系统版本 ≥ Ubuntu 22.04，Python ≥ 3.10
- [ ] 磁盘剩余 ≥ 40 GB
- [ ] 已确认采集网卡名
- [ ] 已确认业务日志路径与格式
- [ ] 已确认管理网段（用于白名单，**不要**把整个私网段加进去）
- [ ] 已和业务方约定封禁 TTL 与解封流程
- [ ] 已备份服务器原有防火墙规则：`sudo iptables-save > /root/iptables.bak`

## 2. 系统安装与基础配置

### 2.1 安装 Ubuntu Server

安装时注意四项：

1. 语言选 English（避免中文路径导致后续脚本异常），时区选 `Asia/Shanghai`；
2. 创建普通用户（例如 `secops`），勾选 "Install OpenSSH server"；
3. 不勾选 "Install third-party software"（减少无关包）；
4. 磁盘用整盘 LVM 或 ext4 均可，`/opt` 建议 ≥ 30 GB。

### 2.2 首次登录与更新

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y curl wget vim unzip net-tools lsof sqlite3 chrony
```

### 2.3 配置静态 IP

查看当前网卡与地址：

```bash
ip -br a
ip route
```

编辑 netplan（文件名可能是 `00-installer-config.yaml` 或 `50-cloud-init.yaml`）：

```bash
sudo vim /etc/netplan/00-installer-config.yaml
```

示例（网卡名、地址、网关按实际修改）：

```yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses: [192.168.152.130/24]
      routes:
        - to: default
          via: 192.168.152.2
      nameservers:
        addresses: [223.5.5.5, 114.114.114.114]
```

应用并验证：

```bash
sudo netplan try      # 有 120 秒确认窗口，按回车接受
ip -br a
ping -c 2 223.5.5.5
```

> VMware NAT 下网关通常是 `192.168.x.2`，宿主机是 `192.168.x.1`。**这两个地址不要加进封禁白名单之外的黑洞**，详见 5.7。

### 2.4 校时（必做）

时间不准会导致告警时间、报告时间线、证书校验全部错乱。

```bash
sudo systemctl enable --now chrony
chronyc sources -v          # 看到 ^* 开头的源即同步成功
timedatectl                 # 确认 Time zone: Asia/Shanghai (CST, +0800)
```

### 2.5 开放管理端口

如果启用了 ufw：

```bash
sudo ufw allow from 192.168.152.0/24 to any port 8000 proto tcp
sudo ufw allow 22/tcp
sudo ufw status
```

> 不要把 8000 暴露到公网；生产建议只允许管理网段，前面再加 nginx + TLS。

## 3. 安装本系统

### 3.1 放置代码

统一放 `/opt/secops`，后续命令都按这个路径写。

```bash
sudo mkdir -p /opt/secops
sudo chown -R "$USER":"$USER" /opt/secops

# 方式 A：有 Git 仓库
git clone <你的仓库地址> /opt/secops

# 方式 B：上传压缩包（在你自己电脑执行）
# scp secops.tar.gz secops@192.168.152.130:/tmp/
tar xzf /tmp/secops.tar.gz -C /opt/secops --strip-components=1
```

确认目录结构：

```bash
ls /opt/secops
# backend  dashboard  deploy  docs  scripts  README.md
```

### 3.2 一键安装

根据形态选参数：

| 场景 | 命令 |
|---|---|
| 演练（业务站点 + 日志） | `sudo bash deploy/install.sh --web-profile` |
| 演练 + 完整请求体 | `sudo bash deploy/install.sh --http-proxy` |
| 生产 + nginx | `sudo bash deploy/install.sh --with-nginx` |
| 生产 + 立即真封禁 | `sudo bash deploy/install.sh --with-nginx --live-firewall` ⚠ |

首次部署**不要**加 `--live-firewall`。先跑通检测，确认无误报后再改。

执行：

```bash
cd /opt/secops
sudo bash deploy/install.sh --web-profile
```

看到以下输出即成功：

```
[install] 部署成功 ✅
{"status":"ok", ...}
  大屏地址：http://192.168.152.130:8000/
  API 文档：/docs ｜ 状态自检：/api/v1/status
```

### 3.3 安装脚本做了什么（排障必读）

| 步骤 | 动作 | 出问题看哪里 |
|---|---|---|
| 1 | `apt install python3 python3-venv libpcap0.8 nmap iptables nftables` | 网络/apt 源 |
| 2 | 创建 `/opt/secops/.venv` 并装 `backend/requirements.txt` + 尝试安装 `google-re2` | pip 源、磁盘；RE2 装不上会警告并回落 python |
| 3 | 给 venv 的 python 加 `cap_net_raw,cap_net_admin` | `getcap` 查看 |
| 4 | 生成 `/opt/secops/.env`（`--web-profile` 用 `deploy/env.web.example`）；`API_TOKEN` 为空时自动生成 | 手工改配置 |
| 5 | 写 `/etc/systemd/system/secops-traffic-guard.service` | `systemctl cat` |
| 6 | `systemctl enable --now` 并自检 `/api/v1/health` | `journalctl -u` |
| 7 | `--http-proxy` 时把 Apache 从 8080 改到 8081，起代理 | 端口占用 |
| 8 | `--with-nginx` 时写 nginx 站点 | `nginx -t` |

### 3.4 手动安装（不用脚本时）

```bash
cd /opt/secops
python3 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install -r backend/requirements.txt

cp deploy/env.web.example .env
vim .env      # 按第 3.6 节逐项确认

sudo setcap 'cap_net_raw,cap_net_admin,cap_net_bind_service+eip' "$(readlink -f .venv/bin/python3)"

# 前台试运行（Ctrl+C 退出）
cd backend
../.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
```

确认无误后再交给 systemd（内容同 3.3 第 5 步）。

### 3.5 检查服务状态

```bash
systemctl status secops-traffic-guard --no-pager
journalctl -u secops-traffic-guard -n 50 --no-pager
curl -s http://127.0.0.1:8000/api/v1/health
```

正常返回：

```json
{"status":"ok","version":"...","db":"ok"}
```

如果失败：

```bash
journalctl -u secops-traffic-guard -n 200 --no-pager | tail -40
ss -lntp | grep 8000            # 端口是否被占
sudo -u "$USER" test -r /opt/secops/.env && echo env-ok
```

### 3.6 逐项确认 `.env`

`.env` 必须在仓库根目录（`/opt/secops/.env`），后端和 systemd 都读这一份。最小可用配置：

```ini
# 说明：这里只列「需要你确认」的项，其余沿用 install.sh 生成的值。
# 行尾不要写 # 注释——systemd 的 EnvironmentFile 会把注释当成值的一部分。
# 基础
DEBUG=false
# 留空由 install.sh 自动生成；手动指定用 openssl rand -hex 24
API_TOKEN=

# 登录（生产保持 true）
AUTH_ENABLED=true
# 留空=首启生成随机密码（journalctl 查看）；不要写死弱口令
ADMIN_INITIAL_PASSWORD=
SESSION_TTL_SEC=43200
SESSION_IDLE_SEC=1800
# HTTPS 部署后改 true
COOKIE_SECURE=false

# 威胁事件 / 规则包
PROTECTED_CIDRS=192.168.152.0/24
THREAT_STORE_ENABLED=true
THREAT_RETENTION_DAYS=7
RULESETS_ENABLED=true
RULES_TIERS=core
RULES_SHADOW_MODE=false
MATCH_BACKEND=auto
TRIAGE_ENABLED=false

# 存储
DB_URL=sqlite:////opt/secops/backend/data/secops.db

# 采集
CAPTURE_MODE=scapy
CAPTURE_IFACE=ens33
BPF_FILTER=ip and (tcp or udp)
TICK_INTERVAL_MS=500

# 响应
AUTO_BLOCK_ENABLED=true
AUTO_BLOCK_MIN_SEVERITY=high
DRY_RUN=true
BLOCK_TTL_SEC=600
FIREWALL_BACKEND=auto
WHITELIST_CIDRS=127.0.0.1/32,::1/128,169.254.0.0/16,224.0.0.0/4

# Web 检测
WEB_DETECT_ENABLED=true
WEB_DETECT_SOURCE=log
WEB_LOG_PATH=/var/log/apache2/access.log
WEB_DEFAULT_DST_IP=192.168.152.130
WEB_DEFAULT_DST_PORT=8080
DETECT_IGNORE_IPS=127.0.0.1,::1
WEB_IGNORE_IPS=127.0.0.1,::1
```

> `DB_URL` 的绝对路径是四个斜杠：`sqlite:////opt/...`（三个斜杠 + 绝对路径）。

改完必须重启：

```bash
sudo systemctl restart secops-traffic-guard
```

后面很多命令会用到 `$API_TOKEN`，先导出（**每开一个新终端都要执行一次**）：

```bash
export API_TOKEN="$(grep '^API_TOKEN=' /opt/secops/.env | cut -d= -f2-)"
echo "${API_TOKEN:0:6}..."      # 能打印前 6 位就说明读到了
```

### 3.7 首次登录

完成 P0 后：

1. 浏览器打开 `http://192.168.152.130:8000/`；
2. 自动跳转 `login.html`；
3. 用户名 `admin`，密码来源二选一：
   - `.env` 里设置了 `ADMIN_INITIAL_PASSWORD` → 用它；
   - 没设置 → 首次启动日志里的一次性随机密码：

```bash
sudo journalctl -u secops-traffic-guard | grep -i "一次性密码\|initial password" | tail -3
```

4. 首次登录会强制改密（≥10 位，含字母与数字）；
5. 打开“规则管理 → 用户与审计（admin）”：填写用户名/显示名/初始密码/角色，点“新建用户”。
   建议角色：`analyst`（日常研判、封禁、导出）、`viewer`（只读值班大屏）。

> 新增用户首次登录会被强制改密；`viewer/analyst` 看不到用户管理区。用户名 2–64 位，支持中文、字母、数字及 `_.@-`，不能含空格；停用用户可在同一列表点“重新启用”；系统禁止把最后一个启用中的 admin 降级或停用。

### 3.8 开机自启与重启验证

```bash
sudo systemctl is-enabled secops-traffic-guard     # enabled
sudo systemctl restart secops-traffic-guard
sleep 3
curl -s http://127.0.0.1:8000/api/v1/health
```

重启后确认：采集模式、规则数、威胁事件时间戳都在更新（见第 8.1 节）。

### 3.9 登录后先认识页面

| 页面 | 地址 | 你要做什么 |
|---|---|---|
| 监控大屏 | `/` | 看整体态势；红色告警弹窗可点详情 |
| 流量监控 | `/traffic.html` | 核对带宽/包速率；导出或封禁可疑源 |
| 威胁告警 | `/threat.html` | 查可疑流量明细；点“详情”看请求包；按标签筛选；导出 CSV |
| 封禁管理 | `/block.html` | 封禁/解封/续期、白名单、告警通道；点“生成报告”出证据 |
| 异常端口 | `/anomaly.html` | 看端口基线与阈值信号（聚合抑制可见） |
| 规则管理 | `/rules.html` | 看规则包装入情况；admin 可切档位/后端/影子模式 |
| 漏洞提醒 | `/vuln.html` | 扫描、查看 CVE、AI 修复建议 |
| 资产管理 | `/asset.html` | 资产台账、指纹、关联告警与漏洞 |

> 旧书签 `response.html` 会自动跳到 `block.html`，不需要改收藏夹。

## 4. 配置采集

### 4.1 三种模式对比

| 模式 | `.env` | 能看到 | 需要 |
|---|---|---|---|
| 日志 | `WEB_DETECT_SOURCE=log` | URL、query、UA、状态码 | 日志读权限 |
| 代理 | `WEB_DETECT_SOURCE=api` + 代理进程 | 完整请求，可选响应 | 改端口 |
| 防火墙/镜像 | `CAPTURE_MODE=firewall` / `mirror`（⏳ 未实现） | 五元组、包长、flags | 抓包权限 |
| 仿真 | `CAPTURE_MODE=demo` | 内置剧本 | 无 |

### 4.2 日志模式（推荐先做）

#### 4.2.1 确认日志路径与格式

```bash
ls -l /var/log/apache2/
tail -n 2 /var/log/apache2/access.log
tail -n 2 /var/log/apache2/other_vhosts_access.log
```

两种常见格式：

```

192.168.152.1 - - [19/Oct/2026:16:00:00 +0800] "GET /x.php?id=1 HTTP/1.1" 200 1234 "-" "sqlmap/1.8"

# vhost_combined（8080 vhost 未单独配 CustomLog 时）
youke-Virtual-Platform:8080 192.168.152.1 - - [19/Oct/2026:16:00:00 +0800] "GET /x.php?id=1 HTTP/1.1" 200 1234 "-" "sqlmap/1.8"
```

#### 4.2.2 授权读取日志

Ubuntu 的 `/var/log/apache2` 默认 `640 root:adm`：

```bash

sudo usermod -aG adm "$USER"
# 必须重新登录（或 newgrp adm）才生效
newgrp adm
tail -n 1 /var/log/apache2/access.log
```

以服务用户验证（systemd 用的是安装用户）：

```bash
sudo -u "$USER" tail -n 1 /var/log/apache2/access.log
```

读不到就说明权限没生效，**不要**用 `chmod 777`，加组即可。

#### 4.2.3 配置 `.env`


#### 4.2.4 验证是否真的读到了

> 以下 API 命令使用 `X-API-Token` 机器调用（登录启用时必需）。先在新终端执行：
> `export API_TOKEN="$(grep '^API_TOKEN=' /opt/secops/.env | cut -d= -f2- | tr -d '[:space:]')"`。

关键字段：

| 字段 | 正常表现 | 异常含义 |
|---|---|---|
| `source_running` | `true` | `false`：tail 线程没起来 |
| `parsed` | 随访问持续增长 | 长期 0：路径错/权限不足/格式不匹配 |
| `skipped` | 不增长或极少 | 持续增长：日志格式不支持 |
| `processed` | 与 `parsed` 接近 | 远小于 `parsed`：队列满或检测线程卡住 |
| `queued` | 个位数 | 持续接近 2000：处理不过来 |
| `dropped` | 0 | 增长：队列溢出，需降规则或提性能 |

#### 4.2.5 日志轮转（否则每天凌晨会"失明"）

logrotate 默认把 `access.log` 改名后新建文件，而本系统是**按文件句柄持续读取**的：轮转后句柄仍指向旧文件，新日志不会进来。表现是"每天凌晨后 `parsed` 不再增长"。

两个处理方式，任选其一：

**方式 A（推荐）：轮转后重启本服务**

```bash
sudo tee /etc/logrotate.d/secops-tail > /dev/null <<'EOF'
/var/log/apache2/*access.log {
    daily
    rotate 14
    missingok
    notifempty
    copytruncate
    postrotate
        systemctl restart secops-traffic-guard >/dev/null 2>&1 || true
    endscript
}
EOF
```

`copytruncate` 保证 Apache 继续写同一文件；`postrotate` 让本系统重新打开文件。

**方式 B：改用原地截断（不重启服务）**

只保留 `copytruncate`，不写 `postrotate`。这种方式下句柄仍有效，但如果一次截断发生在读取中途，可能丢几行。

> 修改后手动验证一次：`sudo logrotate -f /etc/logrotate.d/secops-tail`，然后访问一次业务，看 `parsed` 是否继续增长。

### 4.4 代理模式（需要完整请求体）

### 4.5 三个名单的区别（最容易搞错）

| 配置 | 作用 | 配错的后果 |
|---|---|---|
| `DETECT_IGNORE_IPS` | 流量检测直接忽略这些源 | 攻击者从这里来也看不到 |
| `WEB_IGNORE_IPS` | Web 检测 + 禁止自动封禁 | 同上，且永不封禁 |
| `WHITELIST_CIDRS` | 封禁前最后一道闸门 | 命中即拒绝封禁，但**仍然告警** |

推荐值：

```ini
DETECT_IGNORE_IPS=127.0.0.1,::1
WEB_IGNORE_IPS=127.0.0.1,::1
WHITELIST_CIDRS=127.0.0.1/32,::1/128,169.254.0.0/16,224.0.0.0/4
```

⚠ **不要**把 `192.168.0.0/16`、`10.0.0.0/8` 整段写进 `WHITELIST_CIDRS`。VMware NAT 下宿主机攻击流量的源地址就是 `192.168.x.1`，一旦白名单覆盖它，封禁会被直接拒绝——这正是"有告警但不封禁"的最常见原因。

### 4.6 采集自检不通过怎么办

| 现象 | 先查 | 处理 |
|---|---|---|
| `parsed=0` | `sudo -u $USER tail <日志>` | 加 `adm` 组并重新登录 |
| `skipped` 持续增长 | 日志首行格式 | 改 Apache 为 combined，或换日志文件 |
| `processed=0` 但 `parsed>0` | `journalctl -u ... | grep -i error` | 检测线程异常，重启并查堆栈 |
| `dropped` 增长 | `queued` 是否接近上限 | 提高 `WEB_QUEUE_SIZE`、关 extended 规则、上 RE2 |
| `mode=demo` | 启动日志的降级原因 | 修权限/网卡，或显式设 `CAPTURE_MODE=scapy` |

## 5. 告警、封禁与通知

### 5.1 先理解 `DRY_RUN`

| 值 | 行为 | 什么时候用 |
|---|---|---|
| `true`（默认） | 判定、告警、写库都正常，**只记录待下发命令**，不改防火墙 | 首次部署、误报标定、演练 |
| `false` | 真正执行 `iptables/nft/firewalld` | 确认无误报后 |

判断当前状态：

```bash
grep '^DRY_RUN' /opt/secops/.env
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/blocks | python3 -m json.tool | grep -i dry
```

### 5.2 封禁后端

```ini
FIREWALL_BACKEND=auto        # auto|iptables|nftables|firewalld|none
FIREWALL_CHAIN=INPUT
```

| 值 | 适用 | 检查命令 |
|---|---|---|
| `auto` | 默认，按可用性挑 | — |
| `iptables` | Ubuntu 20.04、CentOS 7 | `iptables -V` |
| `nftables` | Ubuntu 22.04+、新系统 | `nft --version` |
| `firewalld` | RHEL/openEuler/麒麟 | `firewall-cmd --state` |
| `none` | 只告警不封禁 | — |

> `FIREWALL_CHAIN` 对 iptables 与 nftables 均生效（nftables 会映射为 input/forward/output hook）。

✅ **nftables 后端已修复**：会自动创建 `inet secops` 表、`blocklist` 集合（单 IP，`timeout`）、
`blocklist_cidr` 集合（`flags interval,timeout`，支持 CIDR）、基础链以及
`ip saddr @blocklist drop` / `ip saddr @blocklist_cidr drop` 两条规则，并在解封后保留空集合。验证：

```bash
sudo nft list ruleset | grep -A4 'table inet secops'
# 应能看到 @blocklist 与 @blocklist_cidr 的 drop 规则
```

如果现场仍是旧版本，升级后重启服务即可；旧集合中的元素会被新规则引用。

### 5.3 TTL 与解封

```ini
BLOCK_TTL_SEC=600       # 10 分钟，演练推荐
# BLOCK_TTL_SEC=1800    # 30 分钟，生产推荐
```

- 后台每 10 秒扫描到期规则并解封；
- 同一 IP 重复封禁只累加 `hits`，不重复下发；
- 手动解封：封禁管理页 → 行操作 → 解封；或调 `DELETE /api/v1/blocks/{ip}`。

### 5.7 ⚠ 把自己封了怎么恢复

**症状**：SSH/网页突然全断，但服务器还在运行。

1. 打开 VMware 控制台（或物理显示器），用本地账号登录；
2. 查看规则：

```bash
sudo iptables -S | grep SECOPS_BLOCK
```

3. 删除所有本系统下发的规则：

```bash
for ip in $(sudo iptables -S INPUT | awk '/SECOPS_BLOCK/ {for(i=1;i<=NF;i++) if($i=="-s") print $(i+1)}'); do
  sudo iptables -D INPUT -s "$ip" -m comment --comment SECOPS_BLOCK -j DROP
done
```

4. 立即停掉自动封禁，防止再次发生：

```bash
sudo sed -i 's/^DRY_RUN=.*/DRY_RUN=true/' /opt/secops/.env
sudo systemctl restart secops-traffic-guard
```

5. 把被误封的地址加入 `WHITELIST_CIDRS`（只加单个地址，不要加整段）。

> nftables 用户看这里：

```bash
sudo nft list set inet secops blocklist          # 单 IP
sudo nft list set inet secops blocklist_cidr     # CIDR
sudo nft delete element inet secops blocklist { 192.168.152.1 }
sudo nft delete element inet secops blocklist_cidr { 192.168.152.0/24 }
sudo nft flush set inet secops blocklist         # 删除全部（应急）
sudo nft flush set inet secops blocklist_cidr
```

> firewalld 用户：`sudo firewall-cmd --list-rich-rules`，用 `--remove-rich-rule='<原规则>'` 删除。

## 6. 规则库与匹配引擎

> 本章用到的 `/api/v1/rules/packs`、`/api/v1/rules/engine` 在 P2 批次上线后可用。

### 6.1 三个规则包与三个档位

| 包 | 条数 | 作用 | 默认 |
|---|---|---|---|
| 入侵检测 | 742（HTTP 633 + 流级 109） | SQL 注入、XSS、命令执行、上传、扫描等 | 只开 core 89 |
| 研判 | 300 | 抑制误报、提级、定性 | 开 |

档位：

| 档位 | 含义 | 默认 | 建议 |
|---|---|---|---|
| `core` | 高置信、低误报 | 开 | 所有环境 |
| `extended` | 覆盖完整，误报未标定 | 关 | 影子模式跑过再开 |
| `lab` | 通用 UA、低置信 | 禁 | **不要上生产** |

### 6.2 按场景选择

| 场景 | `RULES_TIERS` | 说明 |
|---|---|---|
| Web 演练 | `core,extended,lab` | 便于观察命中，但要接受噪声 |
| 生产 Web | `core` → 标定后 `core,extended` | 先稳后全 |
| 网关/旁路 | `core` + 只开流级类别 | 内容规则在网关上看不到 |
| 文件服务器 | `core` + 病毒特征 | 不开 HTTP 规则 |

### 6.4 安装 RE2（规则多时必装）

```bash
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/rules/engine | python3 -m json.tool
```

| `matcher_backend` | 含义 |
|---|---|
| `python` | 逐条正则，696 条约 2.6 ms/请求 |
| `re2` | 多模式预筛，696 条约 0.095 ms/请求 |

**在线安装**：

```bash
cd /opt/secops
.venv/bin/pip install google-re2
.venv/bin/python -c "import re2; print('re2 ok')"
```

**离线安装**（服务器不能出网）：

```bash
# 在一台同样系统、同样 Python 版本的联网机器上
pip download google-re2 -d /tmp/re2wheels
# 拷贝到服务器
scp /tmp/re2wheels/*.whl secops@192.168.152.130:/tmp/re2wheels/
# 服务器上
cd /opt/secops
.venv/bin/pip install --no-index --find-links /tmp/re2wheels google-re2
```

切换：

```bash
sudo sed -i 's/^MATCH_BACKEND=.*/MATCH_BACKEND=re2/' /opt/secops/.env
sudo systemctl restart secops-traffic-guard
```

验证：

```bash
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/rules/engine | python3 -m json.tool
```

预期：

```json
{
  "matcher_backend": "re2",
  "matcher_patterns": 1144,
  "compile_ms": 122,
  "candidates_pct": 1.0,
  "matcher_fallback_rules": 2
}
```

`fallback_rules` 是用了 lookaround、RE2 不支持、退化为逐条匹配的规则。少量（个位数）正常，仍能命中。

### 6.6 手写 / 上传规则（P5，当前版本未启用）

> **本版本规则管理页只读**：可以查看规则包、档位、匹配后端与编译耗时；没有自定义规则上传/
> 试跑/版本回滚入口。请勿按下面的 P5 界面操作。需要紧急加规则时，由研发修改
> `backend/data/rulesets/intrusion_rules.json`（保持 `taxonomy` 类别已定义）后，
> 管理员在规则管理页点“重载全部规则”，或调用 `POST /api/v1/rules/reload`。

以下为后续版本设计，供评审使用。

**手写**：

1. 规则管理 → 自定义规则 → 新建；
2. 选模板（HTTP / 流级 / 研判 / 病毒）；
3. 填写字段：

```json
{
  "id": "CUS-0001",
  "title": "内部接口越权访问",
  "category": "api_abuse",
  "severity": "high",
  "confidence": "medium",
  "match_targets": ["path", "query"],
  "patterns": ["/internal/admin/(export|delete)"],
  "path_regex": "^/api/",
  "tier": "extended",
  "tags": ["越权", "内部接口"],
  "description": "内部管理接口被外部直接访问",
  "remediation": "在网关层限制来源网段，接口加鉴权"
}
```

4. 点"校验"：通过后点"试跑"，贴一条真实请求看是否命中；
5. 保存 → 选择是否立即启用 → 生效。

**上传**：

1. 规则管理 → 上传；
2. 选文件（`.json` / `.yaml` / `.rules`，≤2 MB）；
3. 先看预览：条数、类别分布、直达数、冲突 ID；
4. 确认后落盘；不勾"立即启用"则只入库不生效。

**校验失败常见原因**：

| 提示 | 原因 | 处理 |
|---|---|---|
| `unknown category` | 类别不在分类表 | 用已支持类别，或先扩展 taxonomy |
| `invalid regex` | 正则语法错 | 按行号修 |
| `lookaround not supported` | 用了 `(?=)`/`(?!` | 改写，或允许降级 |
| `duplicate id` | ID 冲突 | 改名，或显式 `override` |
| `too slow` | 试跑超 200 ms | 收窄正则 |

**回滚**：规则管理 → 版本历史 → 选上一版本 → 回滚。回滚后核对规则数与 SHA-256。

### 6.7 规则变更纪律

| 环节 | 要求 |
|---|---|
| 变更前 | 备份 `rulesets/` 与 `custom_rules/`；记录变更单号 |
| 变更中 | 先 `dry_run` 预览，再启用；一次只改一个包 |
| 变更后 | 观察 30 分钟：告警量、误报、`match_us_avg` |
| 回滚条件 | 误报明显上升、CPU 上升 > 20%、规则加载失败 |
| 记录 | 谁、何时、改了什么、影响条数、回滚版本 |

### 6.8 影子模式（上线前必做）

```ini
RULES_SHADOW_MODE=true
```

效果：规则照常匹配并写 `threat_events`，但**不产生告警、不封禁**。页面顶部会显示黄色横幅。

标定流程：

1. 开 7 天，覆盖业务高峰与低谷；
2. 每天导出命中 Top 50 规则与样本；
3. 人工判真/假，算误报率；
4. 误报 > 30% 的规则降 `lab` 或加 `path_regex`；
5. 误报 < 5% 的 `extended` 规则可升 `core`；
6. 完成后关闭影子模式，恢复 `DRY_RUN=true` 观察 1 天，再考虑自动封禁。

## 7. 接入被测 Web 业务站点

> 仅对授权资产做检测；实验环境不要把 8080 暴露到办公网或公网。
> 本节以一个跑在 8080 的 Apache 站点为例，换成 Nginx/Tomcat/Node 业务同样适用：
> 系统只依赖「访问日志 + HTTP 响应」两件事，不依赖业务用什么技术栈。

### 7.1 准备业务与运行环境

```bash
sudo apt update
# 按业务需要安装运行时（示例：PHP 业务）
sudo apt install -y apache2 php php-mysql php-xml php-mbstring unzip
sudo systemctl enable --now apache2
```

把业务发布包放到站点根目录：

```bash
sudo rm -rf /var/www/html/*
sudo unzip -q ~/webapp.zip -d /var/www/html
sudo chown -R www-data:www-data /var/www/html
```

业务自身的数据库、缓存等按它自己的文档初始化——检测系统不需要了解业务表结构。

### 7.2 配置 8080 站点与访问日志

```bash
# 端口只加一次
grep -q '^Listen 8080' /etc/apache2/ports.conf || echo 'Listen 8080' | sudo tee -a /etc/apache2/ports.conf

sudo tee /etc/apache2/sites-available/webapp.conf > /dev/null <<'EOF'
<VirtualHost *:8080>
    DocumentRoot /var/www/html
    <Directory /var/www/html>
        Options FollowSymLinks
        AllowOverride All
        Require all granted
    </Directory>
    ErrorLog ${APACHE_LOG_DIR}/webapp_error.log
    # combined 是 Web 攻击检测的输入格式（含来源 IP、请求行、状态码、UA）
    CustomLog ${APACHE_LOG_DIR}/access.log combined
</VirtualHost>
EOF

sudo a2ensite webapp
sudo a2enmod rewrite
sudo apache2ctl configtest
sudo systemctl reload apache2
```

日志落在 `/var/log/apache2/access.log`，格式 `combined`。若沿用默认 vhost
（没有单独 CustomLog），日志会在 `other_vhosts_access.log`（格式 `vhost_combined`），
系统同样支持，把 `WEB_LOG_PATH` 指过去即可。

### 7.3 确认业务可用

1. 浏览器打开 `http://<Ubuntu-IP>:8080/`，确认首页正常；
2. 有登录页的业务，用测试账号登录一次，确认关键页面可访问；
3. 需要登录后才能被漏扫覆盖时，把该测试账号写入 `.env`：

```bash
WEBAPP_SCAN_USERNAME=your_test_user
WEBAPP_SCAN_PASSWORD=your_test_password
```

### 7.4 与检测系统联动

```bash
# 确认日志可读
sudo -u "$USER" tail -n 1 /var/log/apache2/access.log

# 确认 .env 指向它
grep '^WEB_LOG_PATH' /opt/secops/.env

# 确认统计在涨
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/web/stats | python3 -m json.tool
```

### 8.1 一键自检

### 8.2 正常流量基线（30 分钟）

1. 用浏览器正常访问业务 10–20 次（首页、列表、搜索、登录）；
2. 观察威胁告警页：应为 **0 条**或仅少量低危；
3. 看 `/web/stats`：`processed` 增长，`dropped=0`；
4. 记录 CPU/内存基线：

```bash
top -b -n 1 -p "$(pgrep -f 'uvicorn app.main:app' | head -1)" | tail -3
```

> 如果正常访问就出现大量 `lab` 规则命中，属预期噪声，关闭 `lab` 档即可。

### 8.3 用例 1：sqlmap（SQL 注入）

在**另一台机器**（攻击机）执行：

```bash
sqlmap -u "http://192.168.152.130:8080/app/demo/sqli/?id=1&Submit=Submit" \
  --cookie="PHPSESSID=<你的会话>; security=low" \
  --batch --level=1 --risk=1
```

预期：

- `/web/stats` 的 `processed` 明显增长；
- 威胁告警出现 `sql_injection`，标签"SQL 注入"；
- 详情能看到 query 中的 payload、状态码 200、方向"外到内"；
- `DRY_RUN=true` 时封禁记录为 dry-run；改 false 后出现 `SECOPS_BLOCK`。

> 拿不到 cookie 时，先用浏览器登录业务站点，按 F12 → Application → Cookies 复制 `PHPSESSID`。

### 8.4 用例 2：nmap 端口扫描

```bash
nmap -sS -p 1-200 192.168.152.130
```

预期：

- 统计检测器产生 `port_scan`（本版本流级执行器未启用，`protocol_anomaly` 流级规则后续批次）；
- 方向"外到内"（需配置 `PROTECTED_CIDRS`）；
- 严重度 high 以上时进入封禁流程。

### 8.5 用例 3：Webshell 上传

用业务站点的上传页面上传一个测试 PHP 文件（内容仅 `<?php echo "test"; ?>`，不要用真实后门）：

```bash
echo '<?php echo "secops-test"; ?>' > /tmp/test.php
curl -s -b "PHPSESSID=<你的会话>; security=low" \
  -F "uploaded=@/tmp/test.php;type=application/x-php" \
  -F "Upload=Upload" \
  http://192.168.152.130:8080/app/demo/upload/
```

预期：

- 威胁告警出现 `file_upload` 或 `webshell`；
- 详情能看到 multipart 请求体（代理模式）与规则 ID；
- 病毒特征文件扫描/隔离属于后续批次（`MALWARE_SCAN_ENABLED=false`）；
- **系统不会删除或修改原文件**（当前版本也不隔离）。

### 8.6 用例 4：封禁与自动解封

1. 确认 `DRY_RUN=false`；
2. 用攻击机触发高危规则；
3. 服务器上确认：

```bash
sudo iptables -S | grep SECOPS_BLOCK
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/blocks | python3 -m json.tool
```

4. 攻击机验证：`curl --max-time 3 http://192.168.152.130:8080/` 超时；
5. 等待 TTL（建议先设 120 秒）后再次访问恢复；
6. 检查审计日志有 `block/unblock` 记录。

### 8.7 用例 5：安全事件报告（P1）

1. 封禁管理 → 选一个已封禁 IP → 生成报告；
2. 打开在线预览，核对 9 个章节；
3. 浏览器"打印 → 另存为 PDF"，确认中文不乱码；
4. 核对报告里的 SHA-256 与接口返回值一致。

|---|---|---|---|
| 1 | 页面打不开 / 502 | 服务没起、端口占用、ufw | `systemctl status`；`ss -lntp \| grep 8000`；`ufw status` |
| 2 | 登录后又跳回登录页 | Cookie 未保存、服务器时间错、`COOKIE_SECURE=true` 但用 HTTP | 校时；HTTP 环境设 `COOKIE_SECURE=false` |
| 3 | 攻击了但威胁页为空 | 日志没读到 | 看 `/web/stats` 的 `parsed`；加 adm 组；核对路径 |
| 4 | `parsed=0` | 路径错、权限不足、文件不存在 | `sudo -u $USER tail <日志>` |
| 5 | `skipped` 持续增长 | 日志格式不是 combined/vhost_combined | 改 Apache 日志格式 |
| 6 | `processed` 远小于 `parsed` | 队列满、检测线程异常 | 看 `dropped`；降档位；查日志 |
| 7 | 有告警但不封禁 | `DRY_RUN=true`、白名单、非直达、严重度不够 | 逐项对照 5.5 |
| 8 | 封禁后自己也断了 | 封了宿主机/管理机 | 控制台执行 5.7 恢复 |
| 9 | 显示“已封禁”但攻击机仍能访问 | ① `DRY_RUN=true` ② 链不对（INPUT/FORWARD）③ firewalld 覆盖 ④ nft 规则未落内核 | 先看 10.3 |
| 10 | 端口扫描没告警 | 采集没抓到、阈值过高 | 看 `/capture/status` 的 `pps`；`tcpdump` 对照 |
| 11 | 抓包报权限错误 | 没有 `cap_net_raw` | `setcap` 或 root 运行 |
| 12 | 规则包加载 0 条 | 路径错、JSON 坏、类别未定义 | 看启动日志 `ruleset:` 行 |
| 13 | 引擎仍是 python | re2 没装或配置没生效 | `pip show google-re2`；`MATCH_BACKEND=re2`；重启 |
| 14 | 想上传自定义规则 | 本版本 P5 未启用 | 由研发改规则包后重载；页面只读 |
| 15 | CPU 高 | 规则全开、scapy 抓包、AI 调用 | 关 extended；上 RE2；换 eBPF |
| 16 | 内存持续上涨 | 队列积压、DFA 内存、留存过长 | 看 `queued`；调 `RE2_MAX_MEM_MB`；清历史 |
| 17 | 磁盘满 | 事件/报告/日志 | `du -sh` 定位；调留存；`journalctl --vacuum` |
| 18 | 报告 404 | 文件被清理、目录权限 | 看 `REPORT_DIR`；重生成 |
| 19 | 大屏不刷新（SSE） | nginx 缓冲、代理超时 | nginx 关闭 `proxy_buffering`；超时 ≥ 24h |
| 20 | 数据库 `database is locked` | SQLite 并发写 | 降批量；切 PostgreSQL |
| 21 | AI 研判一直"待人工" | 没配 Key、网络不通、超时 | 这是设计降级；配 `LLM_API_KEY` 或忽略 |
| 22 | 时间线错乱 | 时区/校时 | `timedatectl`；`chronyc sources` |

### 10.2 三个最常被问的问题

**Q1：为什么有告警，但封禁列表里没有？**

按顺序查：

```bash
grep -E '^(DRY_RUN|AUTO_BLOCK_ENABLED|AUTO_BLOCK_MIN_SEVERITY|WEB_AUTO_BLOCK_REQUIRES_DIRECT)' /opt/secops/.env
grep '^WHITELIST_CIDRS' /opt/secops/.env
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/blocks | python3 -m json.tool | tail -20
```

九成是 `DRY_RUN=true` 或白名单覆盖了源 IP。

**Q2：为什么日志明明有攻击，系统没反应？**

```bash
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/web/stats | python3 -m json.tool
```

- `parsed` 不涨 → 没读到日志（权限/路径/格式）；
- `parsed` 涨、`processed` 不涨 → 队列/线程；
- 两者都涨、没有命中 → 规则没开或 payload 在 body（日志看不到）。

**Q3：开了全量规则后 CPU 到 80%，怎么办？**

```bash
grep '^RULES_TIERS' /opt/secops/.env
curl -s -H "X-API-Token: ${API_TOKEN}" http://127.0.0.1:8000/api/v1/rules/engine | python3 -m json.tool
```

顺序：① 降到 `core`；② 装 RE2 并切 `MATCH_BACKEND=re2`；③ 仍高则查采集模式（scapy 每包拷贝）；④ 最后才考虑多进程分片。

### 10.3 显示"已封禁"，但攻击机还能访问

这是最危险的一类故障：界面显示成功、库里也有记录，但内核没拦。按后端分别验证。

**先确认后端类型**：

```bash
grep '^FIREWALL_BACKEND' /opt/secops/.env
```

**A. iptables**

```bash
sudo iptables -S INPUT | grep SECOPS_BLOCK
# 应有：-A INPUT -s 192.168.152.50/32 -m comment --comment SECOPS_BLOCK -j DROP
```

没有规则 → 看是不是 `DRY_RUN=true`，或白名单拦截（`/blocks` 返回的 `message` 会写原因）。

规则存在但仍不通 → 看链：

```bash
sudo iptables -S FORWARD | grep SECOPS_BLOCK
```

网关形态要封转发流量，必须把 `FIREWALL_CHAIN` 改成 `FORWARD`。

**B. nftables（已修复，按下面核对）**

```bash
sudo nft list set inet secops blocklist        # 单 IP 在集合里吗？
sudo nft list set inet secops blocklist_cidr   # CIDR 在集合里吗？
sudo nft list ruleset | grep -A4 'table inet secops'
```

应同时看到基础链与 `ip saddr @blocklist drop`、`ip saddr @blocklist_cidr drop`。若没有，先确认服务已重启到新版本；
仍缺失则手工补建（仅应急）：

```bash
sudo nft add chain inet secops input '{ type filter hook input priority 0; }' 2>/dev/null || true
sudo nft add set inet secops blocklist_cidr '{ type ipv4_addr; flags interval,timeout; }' 2>/dev/null || true
sudo nft add rule inet secops input ip saddr @blocklist drop
sudo nft add rule inet secops input ip saddr @blocklist_cidr drop
```

**C. firewalld**

```bash
sudo firewall-cmd --list-rich-rules | grep SECOPS
sudo firewall-cmd --get-active-zones
```

rich rule 加在了错误 zone 就不会生效；确认 `FIREWALL_CHAIN` 与业务网卡所在 zone 一致。

**最后用攻击机复核**：

```bash
curl --max-time 3 -v http://192.168.152.130:8080/   # 应超时
ping -c 2 192.168.152.130                           # 若只封 TCP，ICMP 仍可能通
```

### E. 术语表

| 术语 | 解释 |
|---|---|
| 五元组 | 源 IP、源端口、目的 IP、目的端口、协议 |
| 方向 | 外到内 / 内到内 / 内到外 / 未知 |
| 保真度 L0/L1/L2 | 只有元数据 / 有完整请求 / 请求响应都完整 |
| core / extended / lab | 规则的三档，默认只开 core |
| 直达规则 | 命中即告警、可绕过聚合的规则 |
| 聚合 | 把多条信号累计成分数，超过阈值才告警 |
| 影子模式 | 只记录不告警不封禁，用于误报标定 |
| TTL | 封禁自动解除时间 |
| DRY_RUN | 只记录不真正改防火墙 |

### F. 应急处置卡（打印贴在机柜）

```
1. 断网/被自己封
   控制台登录 → sudo iptables -S | grep SECOPS_BLOCK
   → 删除规则（见 5.7）→ 设 DRY_RUN=true → 重启服务

2. 服务起不来
   journalctl -u secops-traffic-guard -n 100
   常见：配置项拼写错、端口占用、数据库权限

3. 磁盘满
   du -sh /opt/secops/backend/data/* | sort -h
   调小 THREAT_RETENTION_DAYS；清理 reports/quarantine

4. 误报告警暴涨
   规则管理 → 关 extended / lab
   或 .env 设 RULES_TIERS=core 后重启

5. 需要立刻停止所有封禁
   .env 设 DRY_RUN=true → 重启服务
   （已下发规则仍生效，需手工删除或等 TTL）
```
